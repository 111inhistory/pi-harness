# Capability 反馈与 MCP 注册排查记录

本文是历史调查记录，不是当前接口契约。记录中的全部 MCP 等待和完整 schema 返回已由后续改动替代。当前行为见[接口契约](../interface-contract.md)和[当前架构](../architecture.md#capability)；尚未修复的激活记忆不一致见[已知问题](../known-issues.md)。

原始现场材料含本机目录、会话标识和应用端点。本文仅保留脱敏后的现象、证据边界与修正结论。

## 现场报告

现场记录报告了以下现象，未在本次文档整理中重新访问应用端点：

- Pi 先启动，被控应用后启动。首次后台连接失败后，未观察到后台重试。
- 同一会话的目录查询尚未显示应用工具，另起的 Pi 进程却显示服务器已连接并返回工具。
- 一次 Capability 调用返回约 42,000 字符，包含共同指引和成员参数；展示稿仅保留约 8,000 字符。
- Capability 返回后不久出现 `toolsAdded` 记录。原始分析把这个时间差解释为工具注册晚于交付。
- 某次结果的 `mcp` 为空，原始分析据此怀疑服务器名称没有展开为工具。

以上内容是现场报告，不单独证明注册、激活、模型声明或外部服务状态之间的因果关系。

## 源码核对后的修正

| 原始推断 | 核对结论 |
| --- | --- |
| Capability 能搜索尚未连接的服务器配置 | Broker 搜索当前已注册目录，不把未注册的服务器配置作为候选 |
| 服务器名称未展开为工具 | 选中 namespace 后已有成员展开路径；不是缺失了名称展开逻辑 |
| 目录查询本身需要等待全部服务器 | 等待来自外层工具调用的 MCP readiness 拦截；后续已移除这层全量等待 |
| `toolsAdded` 的时间就是注册完成时间 | 该记录可表示请求声明变化，不能单独确定工具注册时刻 |
| `mcp: []` 证明工具没有注册 | 增量交付会过滤已激活成员，空数组不足以证明注册失败 |
| 展示稿截断证明模型输入被截断 | 展示、序列化后的模型请求和提供方接收是不同边界，需分别验证 |
| 同一脚本内重新查询即可看到新激活工具 | Codemode 固定执行开始时的工具快照，新工具从下一次调用使用 |

独立进程的连接状态不能替代原会话的注册目录。未观察到后台重试，也不能推出 SDK 在实际工具调用时永不恢复连接。

## 后续实现

内部 step 改为字段投影，模型只接收精简候选和同次发现中的重复 ref。宿主保留完整成员、接口和指引。最终交付刷新资格、保存选择、激活工具，再按实际激活集筛选可见结果。

规范分支记忆提供完整共同指引，公开结果不再重复正文。Codemode 目录查询不等待全部 MCP；实际嵌套调用继续经过原生工具管线。Harness 没有新增主动重连或连接恢复状态机。

以下回归验证了对应边界：

- [模型请求中的反馈完整性](../../test/typed/capability-feedback-sdk.test.ts)：大 namespace 的精简反馈是完整 JSON，重复命中仍可选择全部成员。
- [Codemode 目录与执行边界](../../test/typed/capability-codemode-boundary.test.ts)：目录查询、真实工具调用和沙箱快照分别执行各自规则。
- [严格 allowlist 的激活记录缺陷](../../test/typed/capability-allowlist-mask.test.ts)：确认可见交付与先写入的规范记录仍可能不一致。

离线 SDK 回归不能证明真实提供方没有额外截断，也不能证明被控应用持续在线。这两项仍需在对应环境核对。
