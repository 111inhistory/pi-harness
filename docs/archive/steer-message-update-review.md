# Steer message 能否在写入历史前更新

> 历史审查记录：结论仅覆盖检查时的代码与环境。当前行为见[接口契约](../interface-contract.md)，未修复项见[已知问题](../known-issues.md)。

## 结论

**可以通过公开的 `message_end` 扩展事件替换这条消息的最终内容。** 不必清空队列，也不必直接修改 SDK 的队列对象。

上一轮只检查了队列更新接口，就得出“交给 Pi 后不能合并”的判断，不完整。Pi 虽然没有按 ID 更新一条队列消息的专用方法，但提供了消息写入历史前的替换接口。

不过，替换处理函数与真正写入历史不是同一个原子操作。如果后面的扩展等待异步操作，期间到达的新内容不会自动加入已经返回的替换结果。这个限制也已复现，不能承诺写入历史前任意时刻到达的内容都进入同一条消息。

## 环境与方法

记录时间为 2026-10-24。使用本机 Pi Coding Agent、Pi AI `1.4.0` 与 Node.js `22.23.4`。

测试创建真实 SDK 会话，使用文件形式的 SessionManager，运行模拟模型和可控制的等待工具。不访问网络，不修改 SDK 或项目实现。

断言同时检查模型收到的内容、当前分支历史和磁盘 JSONL，避免只改到请求投影、没有真正保存。

## 支持的替换接口

Pi 文档明确允许 `message_end` 返回替换消息，只要求保持原来的 `role`。通知是 `custom` 消息，因此可以返回更新后的 `custom` 消息。

调用顺序是：

1. steer 消息从队列取出。
2. Pi 发出该消息的 `message_start`。
3. Pi 发出 `message_end`，等待扩展返回替换消息。
4. Pi 将最终消息写入会话历史。
5. 后续模型请求使用这条最终消息。

候选用法是：给每组通知一个标识，放入 `details`。第一条消息作为 steer 入队；后续同组内容先更新本地记录。`message_end` 遇到本项目的这条消息时，读取当前记录，返回合并后的正文与附加信息。

这只是验证过的实现机制，不是已完成的产品实现。应只匹配本项目的消息类型和标识，不改用户消息或其它扩展的内容。

## 七个对照场景

| 场景 | 结果 |
| --- | --- |
| 入队后重新赋值调用方原对象的正文和附加信息 | 不更新队列中的消息 |
| 修改 `peekQueuedMessages()` 返回的消息对象 | 本版本会改变队列内容；这是共享对象引用的效果，不是文档规定的单条更新操作 |
| 通知仍在队列中，完成事件更新本地记录；`message_end` 返回合并内容 | 模型、历史和磁盘都只有一条合并通知 |
| 队列已取出通知，暂停在 `message_start`，此时才到达完成事件 | `message_end` 仍能合并；模型、历史和磁盘一致 |
| 同时有用户 steer 消息 | 只替换本项目通知；用户消息仍正常投递和保存 |
| 本项目已返回替换结果，后续 `message_end` 处理函数暂停，此时完成事件才到达 | 历史尚未写入，但新内容没有自动进入旧替换结果 |
| 第一条通知已保存，完成事件另建一组通知 | 原历史不变，完成事件作为第二条 steer 保存 |

七个场景的断言均通过。“负向对照通过”表示确实观察到表中的限制，不表示负向写法适合用于实现。

第四个场景还确认：**队列里找不到消息，不代表消息已经写入历史。** 因此仅通过预览队列来决定还能否合并，不足以覆盖全部阶段。

## 没有找到的接口与不采用的办法

- 公共 API 没有按队列消息 ID 更新或移除单条 steer 的方法。
- `peekQueuedMessages()` 只预览下一轮选中的消息，默认不是全部队列。不能用它判断所有本项目通知是否仍在等待。
- `clearQueue()` 清空全部 steering 和 follow-up 队列，不适合只更新一条通知。当前返回值还不能完整还原所有自定义消息。
- UI 的“取回消息编辑”也使用清空队列再放回编辑器的方式，不是单条队列更新接口。
- 已保存条目的 `context_edit` 会新增历史编辑记录，不属于 D1 的“写入前合并”，不用于回写旧通知。

## 对 D1 的含义

D1 包含两层意思，应分别说明：

- **已经写入历史的不再修改：可以遵守。** 采用 `message_end` 替换，不修改已保存的旧条目。
- **入队后、写入历史前仍可合并：存在受支持的实现方式。** 包括通知已经出队但尚未进入 `message_end` 的情况，不必提前延迟到工具结束才入队。

但“直到实际写入历史的最后一刻都能合并”不是当前接口的保证。实际方案应在本项目的 `message_end` 处理函数生成最终内容时结束本组；此后到达的新内容另组投递。这个截止点比物理写入历史稍早，应明确说明，不能偷偷当成完全相同。

本轮没有修改 D1 的产品决定。实现方案仍应说明这个限制，再确认是否采用。
