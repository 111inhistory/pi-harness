# Capability 批量搜索与增量提交草案

**状态：历史草案，保留讨论记录。** 当前实现见[接口契约](../interface-contract.md#内部批量检索与增量提交)和[架构](../architecture.md#capability)。实现未采用首次搜索独立状态、Broker 批次快照或正常空结束判为失败的提案；实际采用单计数上限加一、复用现有 Broker、正常空结束保留 `ok` 语义。

## 1. 目标与已确认方向

公开入口保持 `capability({})`。Main 仍等待一次最终返回，不消费内部中间结果。

内部检索会话改为批量搜索、增量提交。零选择次数达到限制，或 Agent 主动结束时，宿主结束检索。模型错误、取消和原有 Budget 仍可中止会话。

失败计数依据**这一轮没有选择资源**，不是搜索零命中。搜索有候选但没有选择，也属于零选择；搜索零命中本身不直接结束会话。

增量提交只更新本次检索的内部累积结果，不立即向 Main 发布、写入分支发现记忆或激活工具。外层返回前仍统一完成保存、激活和接口投影。

## 2. 当前实现与改动范围

当前实现依据 `src/capability-agent.mjs`：

- `capability_search` 每次接收一个 `query`，调用 Broker 搜索。
- `submit_result` 接收本次会话已搜索到的 refs，接受后立即结束内部执行。
- 宿主只保留一份最终 `submission`；没有提交时，错误或 Budget 结束会返回空的失败结果。
- 外层 `extensions/capability.mjs` 等待检索结束，先保存发现记录，再激活工具。

建议只更换内部协议和收尾规则。保留公开入口、原生内部 Session、BM25 排序、精确 ref 查找、namespace／MCP 分组、角色排除、local-only 与现有 Budget。

不引入额外 Subagent、任务队列或第二个模型协调器。

## 3. 一个内部工具：`capability_step`

建议用一个工具替代 `capability_search` 和 `submit_result`，不保留旧名称别名：

```json
{
  "queries": ["document formatting", "local PDF tools"],
  "refs": ["namespace://document_tools"],
  "finish": false
}
```

| 字段 | 含义 |
| --- | --- |
| `queries` | 下一批并行执行的本地查询；非结束调用应提供非空数组 |
| `refs` | 本轮选中的资源；只接受此前已返回给该检索会话的 refs，可为空 |
| `finish` | 主动结束；为 `true` 时，`queries` 应为空，仍可提交最后一批选择 |

`src` 不再作为模型参数：当前只允许本地搜索，由宿主固定。

### 搜索与提交的顺序

**同一次调用提交上一批的选择，同时发起下一批搜索。** 模型不能在发出查询时就评估尚未返回的新候选。

每次调用按以下顺序执行：

1. 校验输入结构。
2. 校验并接受 refs，累积有效选择；逐项返回未知 refs，不因某个无效 ref 丢掉其他有效选择。
3. 结算上一批候选对应的零选择次数。
4. 若主动结束或达到计数限制，停止，不执行新查询。
5. 否则，并行搜索 `queries`，返回各查询结果，供下一次调用选择。

工具回执应明确区分新接受、已经接受和拒绝的 refs。没有执行的新查询不应伪装成零命中。

回执示意（仅供内部 Agent 使用）：

```json
{
  "selection": {"accepted": [], "alreadySelected": [], "rejected": []},
  "searches": [{"query": "document formatting", "status": "ok", "tools": [], "mcp": [], "skills": []}],
  "noSelectionCount": 1,
  "noSelectionLimit": 3,
  "endReason": null
}
```

`searches[].status` 描述单条搜索是否执行成功；外层最终 `status` 描述累计成果的交付状态。搜索成功但零命中时，搜索状态仍可为 `ok`。

### 首次搜索与主动结束

首次调用尚无候选可选，因此建议作为准备阶段，不结算零选择。第一次候选返回后，下一次调用才结算该批选择。

最后一次调用可只提交 refs 并设置 `finish: true`。宿主用 `terminate: true` 结束，不再调用模型生成总结。

若模型自然结束而未设置 `finish`，建议同样结算已累积结果，不再要求补一次独立提交。提供方错误不属于主动结束。

示例流程：

```text
调用 1：refs=[]，queries=[A,B]       → 返回第一批候选，不计零选择
调用 2：refs=[第一批选择]，queries=[C] → 接受选择，结算第一批，返回第二批
调用 3：refs=[第二批选择]，finish=true → 接受选择，统一收尾并返回 Main
```

## 4. 零选择计数

建议内部字段命名为 `noSelectionCount`，与搜索执行错误区分。

| 一轮结算结果 | 计数建议 |
| --- | --- |
| 有新增且通过校验的选择 | 不增加 |
| 返回了候选，但没有选择 | 加一 |
| 没有候选，也没有选择 | 加一 |
| 只提交未知 refs，没有接受任何选择 | 加一 |
| 只重复已接受 refs，没有新增选择 | 建议加一，待确认 |

计数按**候选批次**结算，不按关键词数量结算。一批四条查询都没有选择，也只增加一次。

建议采用累计计数：有选择时不增加，但不清零。这样一次选择不会抵消此前累计的空转次数。宿主只判断 ref 是否有效，不推断资源是否语义相关；相关性仍由 Agent 判断。

计数达到上限后，宿主结束内部执行，并返回此前已接受的全部选择。搜索异常另作诊断记录；不把异常当作本地没有资源的证据。原有模型调用数、时间和取消限制继续生效。

## 5. 批量搜索的执行边界

建议 Broker 增加 `searchBatch`，一批内并行处理查询，按输入顺序返回结果。单条查询失败不取消其他查询。

同批可共享一次工具资格／Skill 元数据快照，以及重复 Skill 文件的读取结果。快照仅在当前批次使用，不跨工具调用缓存资格。

各查询仍独立召回、排序和限制候选数量。共享快照应只读；不共享被某条查询修改过的评分或正文拼接对象，避免并行重排互相污染。

结果保留各查询的归属，不先混成一个无法区分来源的候选池。宿主另用累计候选表校验 refs，用累计选择集合去重。

建议限制单批查询数，避免一次批量搜索放大目录扫描和正文读取。具体上限见待确认项。

## 6. 最小运行状态

在现有检索 Run 中保留以下数据即可：

- 累计候选表：`ref → 已返回的候选`。
- 累计选择集合：已通过校验的 refs。
- `noSelectionCount`。
- 是否有待结算的候选批次。
- 结束原因；未结束时为空。
- 现有 warnings、coverage、Budget 和 Session。

`capability_step` 使用 SDK 的 `executionMode: "sequential"`，串行更新这些状态；只有一批内部的查询并行。结束后不再接受新选择或执行新查询。

不新增独立持久化检查点。增量选择保存在本次调用的宿主内存中；模型失败时可保留，整个进程退出时不承诺恢复。

## 7. 收尾与 `ok / partial / failed`

建议状态描述**本次发现是否正常交付**，不声称已证明本地资源不存在，也不声称所有业务需求都已覆盖。

| 情况 | 建议状态 |
| --- | --- |
| 主动结束，有可交付选择，保存和激活正常 | `ok` |
| 零选择次数达到限制，但此前已有可交付选择 | `partial` |
| Budget、超时或模型故障截断会话，但外层仍有效且有可交付选择 | `partial` |
| 部分选中工具最终未能激活，但仍有可交付成果 | `partial` |
| 没有可交付选择，包括主动空结束或达到限制后仍为空 | `failed` |
| 分支发现记录保存失败 | `failed`，不宣告选择成功，不新增激活 |

搜索曾经返回零候选，不直接决定最终状态。某次搜索错误被后续搜索弥补，也不必仅因历史 warning 把最终结果判为 `partial`。

外层处理顺序仍是：

```text
内部会话结束
  → 汇总已接受选择与结束原因
  → 保存分支发现记录
  → 激活选中工具
  → 按当前工具声明投影接口
  → 一次返回 Main
```

外层保存或激活失败应参与最终状态判定，不能只看内部会话的结束原因。

调用方取消或分支切换时，应沿用现有执行失效边界，不把中间成果写入新分支，不在失效调用上新增激活。保留内部选择不等于承诺取消后仍能交付。

### 对 Main 的信息

保留选中的 tools／MCP／Skills 和现有 coverage。`partial`／`failed` 应说明结束原因，不能只给一个空数组。

零选择计数、查询结果、评分和完整错误诊断留在内部，不向 Main 返回未选择的资源目录。

现有 `missingCapabilities` 由空查询推导缺口的逻辑也应调整。零命中和零选择都不能直接充当“本地不存在该能力”的断言；字段是否继续保留、是否改由 Agent 明确报告，需单独确认。

## 8. 实施位置与回归

| 位置 | 修改内容 |
| --- | --- |
| `src/capability/contracts.ts` | 新内部工具 schema、批次上限；删除旧工具契约 |
| `src/capability-agent.mjs` | 累计选择、批次结算、结束判断、保留中间成果的收尾逻辑 |
| `src/capability/broker.ts` | 批量入口、同批只读快照与查询隔离 |
| `extensions/capability.mjs` | 统一发布；保存、激活与最终状态一致 |
| `src/capability/result.ts` | 对 Main 表达部分结果和结束原因，不泄露候选目录 |
| `prompts/capability-*.json` | 批量搜索、上一批选择、计数与结束说明 |
| Capability 单元测试与真实 SDK 本地模型场景 | 按新协议验证数据和控制流，不锁定具体文案 |

重点回归：

- 首次搜索不误计零选择；命中与选择是两种事实。
- 一批多查询只结算一次，部分查询失败不丢其他结果。
- 有效、重复、未知 refs 的处理可区分。
- 有选择后继续搜索，不因第一次接受 refs 而提前结束。
- 达到限制后不执行新查询，也不再发模型请求。
- 模型故障或 Budget 结束后保留之前的选择。
- 主动结束无需多一次总结请求。
- 最终保存失败仍关闭交付，角色排除与 local-only 不变。
- Main 只收到累计选中资源，取消不越过分支失效边界。

## 9. 待确认项

1. 零选择上限：建议先取 **3 次**，宿主固定，不作为模型输入。
2. 计数采用累计而非连续；重复提交已选 refs 不算新增选择。是否采用本草案建议？
3. 首次搜索作为准备阶段，不计零选择。是否采用本草案建议？
4. 状态采用第 7 节规则，正常空结束为 `failed`。是否符合期望？
5. 单批查询上限：建议先取 **4 条**。数字是提案，不沿用 Subagent 并发限制。
6. `missingCapabilities` 的后续语义，不继续从空查询自动推断。
