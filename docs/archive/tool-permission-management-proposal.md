# 工具权限管理提案

## 状态与目标

状态：三态管理接口已落地，提案归档。当前实现仍有旧来源授权和效果一致性缺陷；归档不表示验收通过。当前契约见[接口契约](../interface-contract.md)，修复与冻结要求见[审计及改写计划](../reviews/rpc-permission-audit.md)。

本文记录工具权限管理的目标设计。工具只有三个管理状态：`not managed`、显式启用、显式禁用。现有 manual 与 blacklist 应收敛到同一份管理数据、同一套查询和修改接口，不维护两套独立列表，也不在两者之外再增加一份协调状态。

权限管理适用于 TUI 用户命令、Preset、Capability、直接工具调用、Codemode 和程序接口。领域能力不依赖 RPC 模式或 Socket。[Harness RPC 独立接口提案](harness-rpc-interface-proposal.md)只负责结构化传输和接入，共用本文规定的领域操作。

以下正文保留设计时的取舍和验收要求，不替代当前契约，也不授权在改写期间增加新功能。

## 三个管理状态

以下名称说明状态语义，不固定代码字段、配置或协议名称。

| 管理状态 | 含义 | 发现与执行 |
| --- | --- | --- |
| `not managed` | 用户未显式接管该工具的启用或禁用 | 按现有 Capability 发现、工具选择和作用域规则工作 |
| 显式启用 | 用户明确启用该工具 | 按用户启用路径生效，仍受 SDK 与适用作用域限制 |
| 显式禁用 | 用户明确禁止该工具 | 不参与模型发现，不能通过 Preset 或其他入口恢复使用，hook 阻止后续调用 |

`not managed` 可以由不存在管理条目表示，不必为所有已注册工具保存默认条目。显式启用和显式禁用是同一目标的互斥状态，修改应直接切换该条目的状态，不要求先操作两份名单。

管理状态与当前 active 集是两个概念。Capability 自动发现并激活工具，不将工具变为显式启用。未启用工具也可能处于显式禁用状态。active 集只表示运行时选择，不作为第二份权限数据。

现有 manual 的用户启用与授权语义应并入三态管理。实现不应保留独立 manual 名单、独立黑名单和额外授权名单，再由调用点拼装结果。现有记录可作为迁移输入，但目标设计只保留一套权威管理状态及其必要持久化记录。

## 管理接口

用户命令与程序接口调用同一领域 API。程序接口不解析 Slash handler、通知或状态栏文本。模型不能调用这些操作自行显式启用或解除显式禁用。

| 操作 | 语义 |
| --- | --- |
| 查询管理状态 | 返回当前管理范围内的工具条目及三态值 |
| 设置显式启用 | 将目标设为显式启用，返回实际处理结果 |
| 设置显式禁用 | 将目标设为显式禁用，返回逐项处理结果及生效范围 |
| 解除管理 | 将目标恢复为 `not managed`，不等于显式启用，也不自动激活 |

黑名单的查询、加入和移除分别是同一管理数据的筛选、设为显式禁用及解除管理，不维护独立数据来源。是否保留面向用户的简写命令可在接口命名时决定。

不增加指定工具的命中规则解释、来源追踪或诊断接口。失败返回必要错误即可。管理操作不得绕过 SDK 限制或祖先作用域限制，也不能把实际激活失败包装为工具已经可用。

## 与命令行和工具选择的关系

前期使用 Pi 1.5.0 真实 RPC 子进程验证了以下行为。激活检查使用现有 Capability 领域 API，未调用真实模型。

| 入口 | 已验证语义 |
| --- | --- |
| `--tools -write` | 初始不激活 `write`；工具仍注册，后续可以再次激活 |
| `--exclude-tools write` | SDK 从当前会话注册表中排除 `write`，不能通过激活恢复 |
| `--tools read,capability` | 普通工具受 allowlist 过滤；MCP 另有原生过滤语义 |
| `--no-tools` | 模型工具被过滤，扩展命令仍注册 |
| `--no-builtin-tools` | 内置工具初始不激活，后续可以再次激活 |
| Preset `tools: ["-write"]` | 调整选择；随后 `/capability enable write` 可以再次启用 |

三态管理不应悄悄改变 `-name` 的工具选择语义。Preset 修改 active 集不自动修改用户管理状态，Capability 的模型发现也不产生用户显式管理记录。各入口均应遵守当前管理状态。

解除管理不能重新注册被 SDK 排除的工具。严格 allowlist 下的 MCP 激活和发现记忆差异见[已知问题](../known-issues.md#严格工具-allowlist-下的激活记忆不一致)，不能用管理状态掩盖实际失败。

工具管理不自动禁用同名扩展命令，也不扩展为 Shell 命令内容规则或整套控制操作权限系统。

## 显式禁用的生效方式

### 发现、查询和执行

Capability、Codemode 的 `ALL_TOOLS`、`describeTool`、`describeNamespace` 等查询读取同一有效管理状态。显式禁用工具不进入发现候选或可用目录，不返回其 schema 和指导。用户管理查询仍可显示该条目。

直接和嵌套工具调用均由 hook 检查。旧脚本已知工具名和参数，也不能绕过显式禁用。子 Agent 不得自行解除祖先限制；统一管理不应扩大现有工具的继承范围。

### 按启用状态和声明方式处理

| 设置显式禁用时的状态 | 立即处理 | 后续处理 |
| --- | --- | --- |
| 未启用 | 从发现和可用工具查询中排除，hook 拒绝调用 | 不增加模型提示 |
| 已启用，具有独立声明 | 向用户发一条通知，通过 hook 阻止调用；保留当前声明 | 下次成功 compaction 时，只定向移除仍被禁用的这些工具 |
| 已启用，处于 Codemode-only 且没有独立声明 | 可以立即从有效工具集中移除，隐藏查询信息并阻止调用 | 不必等待 compaction；原始注册保留 |

移除不卸载扩展、不删除原始定义，也不重连 MCP。已经开始的调用不自动取消，Agent 不自动停止。

解除管理不自动激活工具。如果尚未 compaction、工具仍在 active 集，则按 `not managed` 的现有准入规则判断，不必先移除再重新激活。主动设为显式启用与解除管理是不同操作。

### 提示与 compaction

只有设置显式禁用前已经启用且实际使用过的工具才向模型提示。其他工具不增加 prompt。使用证据复用已有分支记录，包含直接和 Codemode 嵌套调用；注册、发现和查询接口不算实际使用，不新增独立使用计数。

显式禁用与 Capability 内部 inherited 检索会话共用“保留声明、尾部提示、hook 拦截”机制。调用方只提供禁止集合和需要提示的集合，内部检索约束不写成用户管理状态。提示复用已有尾部追加路径，不另写头部 system section 或维护第二套提示投影。

compaction 后的声明清理可共用底层移除投影；集合、时机和文案由调用方提供。普通 `pruneOnCompaction` 允许再次通过 Capability 发现，显式禁用不允许，不能直接复用其重新激活文案。

成功 compaction 按当前管理状态定向移除显式禁用工具，不以本次修改为理由额外移除其他工具。普通 prune 继续按自身规则工作，同一工具同时涉及两者时使用禁止语义。compaction 失败不提前执行延迟移除，hook 继续拦截；压缩前已不再显式禁用的工具不作为该清理目标。

## 机制复用与迁移

[AGENTS.md](../../AGENTS.md)要求避免重复权威状态。实现应扩展现有准入和作用域机制，将现有 manual 与 blacklist 管理收敛到同一结构与解析路径，不保留两套列表或兼容包装。

已有 blacklist 的调用拦截、目录过滤、Codemode 处理和 compaction 定向清理可保留。改动重点是将其与 manual 的管理数据、匹配和准入判断合并为三态，并调整现有管理入口及持久化记录；不重做整个执行流程，不为统一管理增加新的服务层。

现有复用基础：

- [manual-tools.ts](../../src/capability/manual-tools.ts)的工具名匹配语义，应在统一管理中承接。
- [admission.ts](../../src/capability/admission.ts)与[scope.ts](../../src/capability/scope.ts)负责准入和祖先限制。
- [activation.ts](../../src/capability/activation.ts)与[enable.ts](../../src/capability/enable.ts)负责实际激活和用户启用路径。
- [Preset](../../extensions/preset.ts)与[修饰符](../../src/preset/modifiers.ts)负责工具选择。
- [retrieval-tools.ts](../../src/capability/retrieval-tools.ts)、[内部检索装配](../../src/capability/extension.ts)和[session-transcript.ts](../../src/session-transcript.ts)提供历史声明保留、尾部提示和 hook 拦截基础。

## 待定项

1. 三态管理的配置结构、持久化位置及分支、会话、项目或全局作用域。
2. 工具名、模式及 MCP／namespace 分组的统一目标语法，重叠目标及尚未注册工具的处理。
3. 对现有和后续子会话的传播方式，以及操作报告的实际生效范围。
4. 现有 manual 配置、用户启用记录与黑名单记录如何一次迁移到统一三态，保留必要权限约束。
5. 管理修改、运行时更新与持久化部分失败时的必要错误表达及恢复方式。

## 验收要求

后续实现应使用真实 SDK 与离线模型验证领域行为，分别覆盖用户命令和程序接口适配。

- 三个状态共用一份权威管理数据；切换和解除管理不产生两套名单的残留。
- Capability 自动发现和激活不变为显式启用，Preset 选择不暗改管理状态。
- 所有入口读取同一有效管理状态，active 不冒充显式启用。
- 所有模式的可用工具查询隐藏显式禁用工具，独立声明保留期间调用仍被 hook 阻止。
- 独立声明在成功 compaction 时定向移除，Codemode-only 可立即移除有效成员，原始注册保留。
- 只有已启用且实际使用过的工具进入模型提示；复用内部检索的机制，不复用普通 prune 的重新发现文案。
- 解除管理不自动激活，SDK 和祖先限制继续生效。
- 覆盖现有和后续子会话、压缩失败、切换、reload、已开始调用和部分失败。

实施后应将生效行为同步到[接口契约](../interface-contract.md)和[当前架构](../architecture.md)。
