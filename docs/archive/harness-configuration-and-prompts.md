# Proposal：Harness 配置与 Subagent 提示词定制

本文已归档。Harness 参数配置与指定提示词段落定制已实现，当前字段、默认值和生效规则见 [Harness 参数配置](../harness-configuration.md)。下文保留实现前的设计讨论，其中的候选字段、待确认项和实施顺序不作为当前契约。

## 目标与范围

用户应能修改执行策略和资源限额，而不必修改生产代码。Subagent 提示词应开放指定段落的替换和追加。

首轮开放以下项目：

| 配置范围 | 候选字段 | 当前行为 |
| --- | --- | --- |
| Subagent 编排 | 最大深度、每个父节点的活跃子节点上限 | 最大深度 2，每个父节点最多 4 个活跃子节点 |
| Subagent Budget | 每层的模型调用次数、活跃时长、总存活时间 | `JOB_BUDGET_BY_DEPTH` 定义 Depth 1 和 Depth 2 |
| Capability Budget | 模型调用次数、活跃时长、总存活时间 | 调用 soft 16／hard 20，活跃 soft 180 秒／hard 360 秒，总存活 600 秒 |
| Capability 搜索 | BM25 参数、各类候选数量、查询词项上限、Skill 正文候选数量与长度 | BM25 `k=0.9`、`b=0.9`、`d=0`；候选上限为 Tool／namespace 8、MCP 8、Skill 6 |
| Capability 进度 | 零新增选择上限 | 反馈上限 3，内部保留一次首轮搜索额度 |
| 启动与路由 | Inherited 工具注册等待上限、分类器重试次数与间隔 | Harness 的注册等待为 10 秒；分类器最多尝试 3 次 |
| Codemode | 沙箱内存上限、默认输出 token 上限 | 当前为 256 MiB、10,000 tokens |
| Subagent 提示词 | 共同工作指引、Inherited 专属指引 | 当前来自 `prompts/subagent-turns.json` |

用户已排除 Worker 名额等待时间和预览行数。首轮不开放这两个配置项。`ALL_TOOLS` 的短描述格式、诊断文本上限和失败原因的显示长度也先保留内部默认值。

Codemode 默认输出上限只作用于 Harness 自己的执行器。脚本显式提供的 `max_output_tokens` 优先于插件默认值。Pi 原生已有的 `codemode.mode`、`inlineBudget` 等设置继续使用 Pi 的入口，不在 Harness 再定义一套。

角色、候选模型、thinking 和角色工具策略继续由 `subagent-routing.json` 配置。Pi 的模型、压缩和原生工具设置继续使用 Pi 自己的配置入口。

## 配置文件与生效时间

推荐的配置入口如下。Harness 参数文件与现有路由文件各自保留职责：

- 全局配置：`$PI_CODING_AGENT_DIR/harness.json`，目录按 Pi 的规则解析。
- 项目配置：受信项目的 `.pi/harness.json`。
- 覆盖顺序：内置默认值 → 全局配置 → 受信项目配置。

普通参数对象按字段合并，数组整体替换。提示词段落按后文的顺序逐层应用，不直接合并 `replace`／`append` 对象。加载器应拒绝未知字段和无效值，并报告字段路径及配置来源。配置缺失时使用内置默认值。配置无效时应报告错误，不应静默改回默认值。

每个根服务使用一份解析后的配置。新的 Subagent 和 Capability 调用使用所属根服务的配置。根服务退役前，配置不变。已经创建的 Job 保留原 Budget，修改配置不追溯改变计数、期限或活跃名额。首轮以重启 Pi 作为明确的生效边界；是否支持 `/reload` 重新读取，应单独验证 SDK 生命周期，不承诺修改文件立即生效。

`subagent-routing.json` 继续使用已有的加载规则。引入 Harness 参数快照，不应顺带修改路由文件的生效方式。

加载器校验配置一次，再把带类型的结果传给各模块。各模块不重复读文件，不重复校验内部字段，也不增加递归冻结或配置副本。

示例字段仅表达结构，最终名称在实施时统一：

## Capability 搜索与反馈

搜索配置只改变当前检索库的参数和资源上限，不增加新的排序层。

### BM25

`search.bm25` 直接映射到 MiniSearch 的 BM25 选项：

| 字段 | 默认值 | 作用 |
| --- | --- | --- |
| `k` | `0.9` | 控制词频饱和；较低值减少重复关键词的得分增益 |
| `b` | `0.9` | 控制字段长度归一化；`0` 不归一化，`1` 使用完整的库内长度归一化 |
| `d` | `0` | BM25+ 的附加项；`0` 保持当前标准 BM25 |

`k` 和 `d` 应为非负有限数，`b` 应在 `0` 到 `1` 之间。MiniSearch 以字段中的不同词项数量计算长度，不直接按字符数计算。增大 `b` 不等于按正文的字节数扣分。

现有索引只有一个 `text` 字段，首轮不提供没有区分作用的字段 boost。名称、描述、参数说明和正文拆成多个字段，或增加语言分词、停用词和模型重排，均不属于本轮配置化。

精确 ref 与 Skill 路径仍直接查找。工具按成员评分，namespace／MCP 组仍取成员最高分。配置不改变这些行为。

### 召回与正文上限

| 字段 | 默认值 | 计算单位与边界 |
| --- | --- | --- |
| `tools` | 8 | 每条查询返回的独立工具或完整 namespace 数量 |
| `mcp` | 8 | 每条查询返回的 MCP 组数量，不是组内工具数量 |
| `skills` | 6 | 每条查询的 Skill 返回数量上限 |
| `skillBodies` | 6 | 元数据初排后，读取正文参与重排的 Skill 候选数 |
| `requestTokens` | 128 | MiniSearch 默认切词后的查询词项上限，不是模型 token 预算 |
| `descriptionChars` | 240 | broker 生成工具／分组候选摘要时的描述字符上限 |
| `skillBodyChars` | 60,000 | 每个 Skill 加入索引的正文字符上限，不是文件读取字节上限 |

首轮保留现有正整数语义，不用 `0` 隐式表示禁用某类资源。`skills` 和 `skillBodies` 分别控制返回量与正文重排的候选量。当前流程只返回这批 Skill 候选，因此最终数量同时受这两个上限约束；配置不引入额外的元数据回退路径。

候选数量只限制召回，不截断已选 namespace 的成员。修改它们也不改变当前本地搜索范围，不触发服务器连接或远端搜索。

### 保持固定的反馈规则

以下行为属于交付契约，不增加开关：

- 同次发现按 ref 去重，首次返回精简候选，之后返回 `repeatedRefs`；之前出现的 ref 仍可选择。
- 宿主保存完整候选。搜索反馈不展开长指引或成员接口，也不截断序列化后的 JSON。
- 最终交付筛掉不能激活的成员。已有声明或查询入口时省略重复 schema，否则保留所需接口。
- 共同指引由规范记忆提供，主返回体不重复正文。
- 搜索和目录查询不等待全部 MCP 后端。重连继续由 Pi 原生行为和用户命令负责。

`noSelectionLimit` 仍统计没有新增接受 refs 的 step。首轮搜索保留一次额外额度，由反馈上限推导；不再开放第二个内部上限字段。

## Subagent 提示词边界

提示词按用途装配。用户不必复制带身份占位符的整段模板。

| 段落 | 来源 | 定制方式 |
| --- | --- | --- |
| 角色指引 | 路由角色的 `instructions` | 沿用现有配置 |
| 共同工作指引 | 内置正文和 `subagent.prompts.common` | `replace`、`append` |
| Inherited 专属指引 | 内置正文和 `subagent.prompts.inherited` | `replace`、`append`；仅用于 Inherited |
| 宿主身份与交付说明 | 宿主装配 | 首轮保留内置内容 |
| 当前任务与批次上下文 | `task`、`context` | 沿用工具入参 |

`replace` 替换对应的可定制段落。`append` 追加到替换后的段落末尾。未指定 `replace` 时，`append` 追加到上一层已经形成的正文末尾。

每个段落按内置正文、全局配置、受信项目配置的顺序应用：

1. 从内置正文开始。
2. 应用全局 `replace`，再应用全局 `append`。
3. 应用项目 `replace`，再应用项目 `append`。

例如，全局把正文替换成 A 并追加 B，项目只追加 C，最终为 A、B、C。项目如果替换成 D，最终为 D，不再保留 A、B。这个顺序避免项目替换正文后，又意外带回全局的旧追加内容。

空 `replace` 表示清空截至该层的可定制段落。空 `append` 不添加内容。提示词字段是普通文本，不执行变量展开、文件导入或表达式。

当前 `context` 同时包含身份和工作指引。实施时应拆分可定制段落与宿主段落。Agent ID、直接父节点、通信地址及最终结果由宿主交付的说明，继续由宿主装配。

Fresh 使用自己的基础 system prompt，再装配这些段落。Inherited 保留继承上下文，再装配当前子节点的段落。共同指引不应在这两条路径中重复追加。替换局部段落不等于替换 Inherited 的整份 system prompt。

本提案不指定新的默认提示词正文。拆分现有正文和引入新默认段落，应由维护提示词的用户单独审阅。如果拆分后没有独立的共同工作指引，`common` 默认可为空；不为提供 `replace` 而编写一段新的默认要求。

## 最大深度与 Budget

最大深度应同时控制派生资格、叶节点工具和每层 Budget。实施时不能只替换 `MAX_AGENT_DEPTH` 的数值。

- 当前默认配置保留 Depth 1、Depth 2 的 Budget。
- 增加最大深度时，配置应为新增深度提供完整 Budget。
- 每个可到达深度都应有最终有效的 Budget；不隐式套用最后一层。
- 子节点处于 `running`、`stopping` 或 `finalizing` 时，仍占用父节点的活跃子节点名额。
- parent-hold 继续使用原 Job 和原 Budget；配置化不改变暂停活跃计时和保留 lifetime 的语义。

## 固定约束与缺陷边界

参数配置不应变成交付正确性的开关。取消与代次围栏、持久化先于激活、角色权限，以及“只增不减只保留成功获得的能力”，继续作为行为要求。

严格 allowlist 下，激活失败却留下成功选择记忆，是现有 defect，不是可选策略。修复应单独完成；不增加“允许记录未激活工具”或关闭激活检查的配置来绕过。

默认值只定义一处，未提供的字段使用默认值。调用方收到解析后的类型对象，不重复解析、不添加兼容别名。除提示词段落的逐层应用外，不引入配置表达式或插件式合并机制。

## 实施与验收

实施分为两批。第一批迁移参数，保持默认行为。第二批拆分提示词段落并开放定制。

验收应覆盖：

1. 缺省配置与当前行为一致。
2. 全局和受信项目覆盖符合约定；不受信项目不生效。
3. 无效字段、Budget 和深度组合给出明确错误。
4. 增加深度后，叶节点工具、派生资格和 Budget 同步变化。
5. Fresh 和 Inherited 都能替换、追加指定段落，宿主身份仍正确。
6. 提示词测试检查段落装配和行为，不锁定用户正文。
7. parent-hold、取消、Budget 和显式消息续跑回归通过。
8. BM25 参数实际传入 MiniSearch，精确引用与分组评分方式不变。
9. 调整召回上限不缩小选中 namespace 的成员集合，重复 ref 仍可选择。
10. 全局提示词替换、追加与项目替换、追加按顺序组合，项目替换不带回旧的全局追加。
11. Codemode 的逐调用输出选项优先于插件默认值，未指定时仍使用默认值。
12. 配置测试检查类型、数值、生效来源和行为，不锁定 routing 提示词的措辞或提供方名称。

尚需确认的设计项是文件名、字段名和项目覆盖策略。本文记录推荐方案，不表示已经实现或已经验收。
