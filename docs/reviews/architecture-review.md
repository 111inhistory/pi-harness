# 核心架构 Review

## 结论

**核心职责有保留价值，但当前职责边界不足以承载已经确认的接口契约。** 本轮倾向于重建 Subagent 的宿主编排与消息投递边界，定向拆分 Capability，而不是整仓重写。

问题不只是文件长。资源生命周期已有可复现缺陷；消息、终态和会话投递也没有统一所有者。继续分别添加判断分支，会扩大跨模块协调成本。

判断原则：保留真实的状态、权限、恢复和资源边界；删除旧设计残留前先确认调用方。文件数量和代码行数不是删改依据。

本文是 Review 和候选职责划分，不是已经批准的重写方案。

## 范围与验证

- 目标依据：`docs/interface-contract.md`，不使用归档文档推断需求。
- 检查范围：Capability、Subagent、两者的 SDK 适配、IPC、存储、提示词投影、测试，以及旧资源引用。
- 检查对象：当前工作区，包含原有的未提交 Capability 提示词记忆改动，不是纯净提交。
- 验证记录（2026-10-24）：在当前 Linux、Node.js 22.23.4 和本机 SDK 环境执行 `npm test`，312 项中 308 通过、2 失败、2 跳过。
- 额外验证：最小会话钩子复现连续切换后未关闭 Main 端点；独立 IPC 测试复现连接未断开时 `close()` 不结束。
- 未审计：真实模型效果、Windows 实机、完整安全攻击面、用户界面、审批界面和生产负载。

下文位置对应本轮工作区代码。后续改动可能使行号变化。

## 现有缺陷

### P1：退役 Promise 永久保留，后续切换跳过当前服务回收

**证据：** `extensions/subagent.mjs:179–231`。`retireService` 发现 `controller.retirement` 存在时直接返回；赋值后没有清空。

第一次替换服务后，后续切换或 shutdown 会复用已经结束的旧 Promise，而不退役当前服务。旧 Job、listener 和持有旧 service 的回调因此可能继续存在。

最小验证使用真实扩展与模拟 Pi 会话钩子，顺序调用 `session_start`、`session_tree`、`session_shutdown`。Main Socket 在 3 个步骤后都存在，shutdown 后没有移除。

**责任问题：** 控制器把“某次退役操作”当成永久状态，却没有将操作绑定到被退役服务及其结束时点。

**回归要求：** 连续切换多个会话或分支后再 shutdown；验证每个旧服务停止工作、端点关闭，新服务仍可运行。

### P1：IPC 关闭等待外部连接，可阻塞退役

**证据：** `src/subagent-socket.mjs:30–79`、`:87–151`；`extensions/subagent.mjs:202–222`。

Socket wrapper 调用 `server.close()`，但不跟踪和销毁已有连接。退役等待 wrapper 关闭，保持连接的客户端可以使等待不结束。

独立验证连接真实端点后调用 `close()`。客户端保持连接时关闭未结束；销毁客户端后关闭结束。该验证不依赖模型执行。

**责任问题：** transport 创建连接资源，却没有完整定义连接的退役路径。取消 Job 不能替代关闭连接。

**回归要求：** 包含不结束的连接、半个报文和多条连接的退役测试；明确退役后不再接收消息的时点。

### P1：Unix 端点没有按系统用户与运行实例定义所有权

**证据：** `src/subagent-ipc.mjs:8–9`、`src/subagent-ipc-unix.mjs:10–18`、`extensions/subagent.mjs:236–240`。

默认根目录是所有系统用户共用的 `/tmp/pi-subagents`。会话目录只使用 Session ID 的短哈希，没有操作系统用户隔离。`mkdir` 不显式设置权限，`unlink` 失败则直接吞掉错误。

作者报告有时以 root 运行 Pi，随后发生 Socket 权限占用问题。按通常的 `0755` 目录权限，root 首次创建共享根目录后，普通用户可能连新会话子目录都无法创建。只删除 Socket 文件不能修复父目录的写入权限。

本轮只读检查发现当前机器的根目录属于普通用户，不能据此声称已复现 root 所有权冲突。该场景目前是作者报告，加上代码可触发条件。

另一个所有权缺口是 `prepare()` 不检查现有路径的类型、所有者或活跃状态，直接尝试删除。两个 Pi 实例使用同一会话地址时，可以互相移除仍在使用的端点；旧实例退出时还可能移除后来实例发布的地址。

**责任问题：** IPC 没有定义系统用户隔离、运行实例所有权和安全回收条件。不能把这些问题都归为“残留文件”。

宜采用用户隔离的私有运行目录，定义实例对端点的占有与释放规则。清理只能处理可确认属于当前实例或已失效的自有资源，不应盲目删除、放宽权限或接管其他用户的路径。具体机制留待设计。

### 退出清理的事实边界

作者报告 Pi 退出后仍留有 Socket 文件。现有正常退出路径依赖 `session_shutdown` → service 退役 → server 关闭 → 端点删除，不是完全没有清理代码。

前述退役 Promise、已有连接和权限错误吞没都能使链路不完整。回归应从实际进程退出观察端点，而不只显式调用 `server.close()`。

SIGKILL 或崩溃时不能承诺运行退出清理。实现还应在后续启动时区分失效端点、活跃实例和非 Socket 路径，再决定是否回收。当前 `prepare()` 的盲目删除不是安全的恢复机制。

### P1：SDK Session 创建成功后、接管前的预算异常会漏掉释放

**证据：** `extensions/subagent.mjs:1411–1423`、`:1582–1593`。

`createAgentSession` 返回后，代码先调用 `throwIfBudgetFailed`，然后才把 `created.session` 赋给清理逻辑持有的 `session`。

如果预算在异步创建期间耗尽，检查抛错时 SDK Session 已存在，但 `finally` 仍只看到空的 `session`，无法调用其 `dispose()`。

这是静态控制流确认的资源所有权缺口，本轮未注入预算耗尽来动态复现。

**责任问题：** 资源取得和清理所有权登记之间存在可抛错操作。应先接管资源，再执行可能失败的后续检查。

### P1：托管发送者绑定存在非对象输入绕过

**证据：** `src/subagent-socket.mjs:253–275`；`extensions/subagent.mjs:815–819`。

托管写入接受 JSON 标量和数组。标量不会绑定 `from`；数组虽然能添加属性，但序列化后丢失该属性。接收端又把缺失 `from` 的报文标记为 Main。

辅助函数验证使用发送者 `sub_01`，分别发送 JSON 字符串、数组和正常对象。前两类到达接收逻辑后被标记为 Main，正常对象保留 `sub_01`。这是输入类别导致的归属错误，不需要调用方提供伪造的 `from` 字段。

该缺陷发生在托管工具自身的路径，不能只用“不要直接连接 Socket”的提示规避。改为纯文本接口时，应无条件构造宿主信封，不再让正文类型决定身份绑定。

本轮没有把本地 Socket 定义为对恶意本机进程的认证边界。直接连接端点的信任模型仍需单独明确。

### P2：失败诊断在公共结果投影中丢失

**证据：** `src/capability-agent.mjs:88–99`、`src/capability-result.mjs:9–12`、`extensions/capability.mjs:147–152`。

发现失败的原因放在 `warnings` 中，公共投影却删除全部 `warnings`。辅助函数验证表明，Main 可以只得到 `status: "failed"` 与空结果，而看不到失败原因。

排序噪声应隐藏，但可恢复错误和内部诊断不是同一类别。公共结果应保留可理解的失败原因，不要求 Main 读取宿主 `details` 猜测。

### P2：历史写入失败被吞掉，仍可能报告历史成功

**证据：** `extensions/subagent.mjs:1463–1471`、`:1612–1647`；`src/subagent-runtime.mjs:1429–1442`。

Clean JSONL 写链中的异常只显示 UI 提示，没有保留失败状态。后续 `job_end` 和摘要写入若成功，收尾 hook 正常返回，Runtime 会记录 `historyState: "ready"`。

因此，部分事件可能缺失，但状态仍表示历史收尾成功。这是瞬时写入失败后恢复情况下的错误路径，不表示每次写入失败都会误报。

**责任问题：** 历史写入器掌握错误，却没有把完整写入结果交给生命周期所有者。

**回归要求：** 注入中途写入失败、末尾写入成功；执行结果保持不变，历史错误仍可查询。

### P2：SDK 兼容边界没有可复现版本基线

**证据：** `package.json` 未声明实际 SDK 依赖，`node_modules` 指向本机安装目录。`extensions/capability.mjs:393–405` 直接依赖 `ModelRegistry.runtime`；Responses 测试也导入 SDK 的 `dist` 文件。

当前 2 个失败分别位于 `test/responses-tool-prefix.test.mjs:34` 和离线 SDK 的 `responses-prefix` 场景。断言期望 `anchorsAdditions === true`，实际为 `undefined`。

后续复核确认，已安装 Pi `1.4.0` 的返回结构没有 `anchorsAdditions`，上述两项仍检查旧字段。不能仅删除断言后宣称投影正确；另外已发现旧前缀代码丢弃同名新版 Schema，应改用实际声明与执行验证。

**责任问题：** SDK 兼容判断分布在功能代码和测试中，却没有明确版本或兼容矩阵。重写前应先记录运行依赖，避免把环境差异当成架构问题。

## 与目标契约的差距

### P1：消息与终态通知分流，缺少统一的待投递所有者

**证据：** `src/subagent-runtime.mjs:1549–1580` 仅为失败产生通知；`extensions/subagent.mjs:613–696` 将普通消息和通知送入不同路径。

- Main 的普通消息使用 `triggerTurn: true` 和 `steer`。
- Main 的终态通知使用 `triggerTurn: false`。
- 子 Agent 的通知追加到 live 或 retained 会话，不启动执行。
- 普通消息还可能位于 Runtime 的 `pending`、adapter 的 `live.pending` 或 SDK 的 steering 队列。

新契约要求正常完成自动通知、通知可唤醒，以及待投递消息与终态合并。当前没有一个位置同时持有尚未交付的消息、终态和执行轮次。

**不宜只把 `triggerTurn` 改为 `true`。** 这不能解决合并，还可能让普通消息和通知分别触发父 Agent。

宜先定义投递边界，再设置单一投递协调者。协调者只合并未交付内容；交给 SDK 后不回写既有消息。这里不预设持久化收件箱、回执、自动重试或固定时间窗口。

### P1：远端候选与本地结果共用 Main 返回通道

**证据：** `src/capability-result.mjs:2–13` 保留 `remote`；`extensions/capability.mjs:147–152` 将公共结果写入工具正文。

删除诊断字段和压缩接口，不等于按接收者分流。审批 UI 可以延期，但远端候选不返回 Main 的边界应先存在。

宜在公共结果构造之前，分开 Main 可用的本地资源和面向用户的远端候选。审批未实现时不自动安装，也不回退为把候选交给 Main。

### P2：传输格式和路由器限制进入调用契约

**证据：** `src/subagent-socket.mjs:253–279` 要求调用方提交 NDJSON；`src/subagent-runtime.mjs:661–668` 按非 ASCII 字符比例拒绝任务。

这两项已明确不保留：纯文本消息封装归 `write`／`msg_write`，英文仅为 Jev 的推荐用法。

任务语言判断不属于拓扑与生命周期 Runtime。消息分帧不属于 Agent。删除这两项外泄责任时，仍应保留输入校验、发送者绑定和普通文件写入行为。

## 结构性问题

### Capability 与 Subagent 通过工具注册表形成隐式依赖

**证据：** `extensions/capability.mjs:120–123` 检查 Subagent 的 `list`／`stop` 工具；`:312–387` 却独立创建内部 SDK Session。`extensions/subagent.mjs:1373–1388` 又直接组装 Capability 扩展。

Capability 并没有通过公开 Subagent 工具执行检索，却以这些工具是否注册作为运行条件。现有权限逻辑还通过 `capability-scope.mjs` 和父 API 桥接进入子会话。

共享父模型环境、上下文和权限边界有真实必要，但不能据此认定公开工具的加载条件也应共享。

后续作者已明确：Capability 应复用 Subagent 的底层执行能力，而不是把二者拆成独立运行的插件。原先“只共用 SDK 适配能力”的候选方向不再采用。

应移除的是通过公开工具注册表判断依赖的做法，不是底层执行依赖。二者配套装配和配置，由内部入口调用；隔离检索与父级资格检查仍应保留。

### Extension 不再是入口，而是多个状态所有者的集合

**证据：** `extensions/subagent.mjs:235–331` 的 service 同时持有 Runtime、liveJobs、retained、Socket、历史写链和 checkpoint 环境；`:1210–1647` 又包含执行与收尾。

Runtime 持有 Actor／Job，service 持有对应会话描述，SDK 持有原生执行状态。区分这些状态有必要，但它们如何同步主要靠散布的回调和闭包。

退役、会话接管和历史错误问题说明，边界尚未把失败路径封装完整。仅将函数搬进多个文件，不会改变所有权。

### 当前查询视图还决定 listener 与广播范围

**证据：** `src/subagent-runtime.mjs:824–825` 的 `listenerGroup` 复用可见窗口；`extensions/subagent.mjs:760–770` 按窗口恢复端点，`:853–859` 也据此选择广播目标。

这使展示数量、listener 缓存和消息目标相互耦合。修改“列表显示多少条”时，可能同时改变保留哪些端点、广播给哪些历史 Agent。

辅助验证先后创建并结束 5 个直接子节点。Runtime 的广播路径枚举全部直接子节点，但 Socket 广播路径只选择最近的 4 个。两条路径确实采用不同的接收集合。

本轮不裁定广播应包含哪些停止节点；该行为应单独确认。无论最终规则如何，展示策略不宜隐式成为通信策略。

### 工具资格缓存存在需进一步证明的失效风险

**证据：** `src/capability-scope.mjs:14–36`。

资格集合只增不减。辅助验证先让中间层缓存工具，再更改其拒绝列表：中间层拒绝该工具，下一层仍可能从中间层的旧缓存取得资格。

尚未发现当前产品运行中动态改角色拒绝列表的路径，因此本项不是已证实的生产越权漏洞。后续应明确拒绝规则是否不可变；若允许更改，应定义缓存失效与后代传播。不要在未确认语义前，把“资格只增不减”当成权限真相。

### Broker 汇集多种职责，提示词分离不是唯一拆分点

**证据：** `src/capability-broker.mjs:679–748` 生成资源快照，`:825–1313` 检索和排序，`:1315–1445` 提取约束和关联，`:1653–1778` 读取资源。

这些职责都有现有调用，不能仅因文件长而删除。应先分清资源目录、检索选择和资源读取的输入输出，再判断规则提取是否值得保留。

提示词目前还分布在工具注册、namespace、内部检索 Agent、子会话上下文和协议包装器。后续分离宜按读者与职责组织，不宜只建一个大字符串文件。

## 候选职责边界

下表是讨论用的责任划分，不要求每行都创建一个类、模块或服务。

| 责任 | 当前分布 | 候选所有者与边界 |
| --- | --- | --- |
| Actor／执行轮次与唯一终态 | Runtime 为主 | 保留 Runtime；不管理 SDK、用户提示词或消息序列化 |
| SDK 执行和资源释放 | Subagent 扩展及 Capability 扩展 | Subagent 内部执行器供两者使用；取得资源即负责释放，SDK 差异留在适配层 |
| 根会话与分支服务寿命 | controller、service、恢复闭包 | Session service；独占激活、退役、分支恢复和 checkpoint 协调 |
| 待投递普通消息与终态 | Runtime、adapter、SDK 多处 | 单一投递协调者；按 Agent 和执行轮次保留待交付内容，决定合并与唤醒 |
| IPC 与纯文本封装 | write wrapper、Socket 回调 | 通信 adapter；绑定身份、封装帧、回收连接，不决定任务终态 |
| 历史派生与写入错误 | 扩展内写链、history helper | 历史写入器；追加并汇总错误，不改变执行结果 |
| 本地发现与远端分流 | Broker、Discovery、公共结果构造 | Capability 流程；先选择，再按接收者分流，最后激活本地工具 |
| 模型可见说明 | 代码内多处字符串 | 提示词资源；区分 Main、子 Agent、内部检索 Agent 和工具说明 |

拟议的执行链：注册任务 → SDK 执行 → Runtime 冻结终态 → 历史收尾 → 发布终态事件 → 投递协调者合并并唤醒父 Agent。

Capability 的拟议链：继承任务上下文 → 隔离检索 → 筛选 → 本地／远端分流 → 本地激活及返回。远端审批后续接入，不阻塞本地流程。

## 保留与清理判断

| 对象 | 判断 | 最强保留理由与处理边界 |
| --- | --- | --- |
| Runtime 的原子批次、唯一终态和 `finalizing` | Keep | 防止取消、执行退出和历史写入互相改写结果；不应压成一个布尔值 |
| 原生 SessionManager、分支 anchor 和身份账本 | Keep | 保护继承、续跑与分支隔离；不另建重复会话存储 |
| Budget、权限资格和执行守卫 | Keep | 承担真实资源与授权边界；提示词记忆不能替代执行权限 |
| 普通消息和终态的交付路径 | Merge | 两类事件不同，但待投递状态、合并和唤醒应有共同所有者 |
| Extension 内部编排形态 | Replace | 行为有必要；资源接管和清理职责应形成可测试边界 |
| NDJSON 调用要求、语言硬拒绝 | Delete | 已有明确产品决定；仅删除外泄负担，不删除内部校验和身份绑定 |
| `prototype/` | Prove first | 没有发现核心运行路径依赖；`package.json:6–8` 的 demo／smoke／cli 仍引用它，删除应同时处理命令和验证用途 |
| `work` | Prove first | 不是核心目标，但有独立扩展、测试和原型调用；应确认是否仍需交付，不能连带删掉 |

| 用户查看和远端审批界面 | Defer | 需求真实，但作者已明确后续再做；保留接口边界，不先造完整控制面 |

## 验证与迁移护栏

1. 固定 SDK 依赖基线，定位现有 2 个测试失败。
2. 为连续退役、连接不结束、Session 接管、发送者输入类别和历史部分写入失败补回归。
3. 为纯文本、多行文本及 JSON 字面内容补通信测试，保留普通文件写入和发送者绑定测试。
4. 为正常完成唤醒、忙碌期间消息与终态合并，以及不同执行轮次不混合补测试。
5. 为审批延期期间远端候选不进入 Main 补边界测试。
6. 迁移测试后再删除旧接口与原型命令，不把旧行为测试无差别搬进新核心。

不应为了减小代码量删掉恢复、权限或历史诊断。也不应为了合并消息引入没有需求的永久消息数据库、回执状态机和自动重试。
