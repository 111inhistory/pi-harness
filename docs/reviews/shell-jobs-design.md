# 提案：Shell 与后台 Job

状态：顶层设计，待实施。普通命令执行、后台任务及输入控制共用现有 Shell Job 后端；不引入独立的 `async_shell` 或终端会话对象。

## 模型接口

| 入口 | 职责 |
| --- | --- |
| Shell 执行入口 | 执行命令；支持显式后台和自动转后台。保留当前平台的 Shell 语义，执行入口是否统一改名为 `shell` 单独决定。 |
| `job_stop(id)` | 停止本执行拥有的 Job，返回停止结果，不重复推送同一份取消结果。 |
| `job_send(id, text, enter?)` | 向 Job 原样发送文本；`enter` 默认 `false`，为 `true` 时在文本后另发一次 Enter。 |
| `job_key(id, key)` | 向 Job 发送按键，沿用现有 `pi-job key` 的按键语义。 |
| 已有 `read` | 按行读 Job 的过滤日志，不新增 poll 工具或模型侧字节游标。 |

`job_send` 与 `job_key` 分开，不提供独立 `terminal` 工具。这两项输入操作不隐式创建 Job。前三项 Job 操作都由宿主绑定当前 Actor 与执行租约，不接收调用方传入的 owner、回调地址或任务目录。

Shell 接受布尔参数 `pty`，默认 `false`。`pty: true` 在 POSIX 分配 PTY，在 Windows 使用 ConPTY；`job_send` 和 `job_key` 操作该终端。`pty: false` 使用普通子进程和管道输出，默认关闭 stdin；`job_send` 和 `job_key` 明确拒绝这类 Job。两类 Job 都支持 `job_stop`。`pty` 只选择执行方式，与 `background` 和 `timeout` 独立。

## Shell 调用语义

| 输入 | 行为 |
| --- | --- |
| `background: true` | 启动后立即返回 Job ID 和过滤日志路径。若同时指定 `timeout`，它仍然是任务执行上限。 |
| 未请求立即后台，未设 `timeout` | 使用 Harness 可配置的自动转后台阈值，默认 60 秒。阈值内完成直接返回；到点仍在运行则返回 Job ID 和日志路径，原执行继续，无默认执行超时。 |
| 未请求立即后台，显式设 `timeout` | 保留现有前台执行及超时行为，不因等待窗口结束转后台。 |

60 秒是普通 Shell 自动交还控制权的默认阈值，不是任务超时。`pi-job create` 是显式选择异步执行，其 CLI `--wait` 默认值保持 5 秒；Shell 入口在复用后端时应显式传入 Harness 的等待阈值，不继承 CLI 默认值。

可转后台的命令从开始就由选定后端受管执行，避免先用 SDK 启动再试图迁移或重跑。现有 `pi-job` 终端后端用于 `pty: true`；非 PTY 路径需要独立的轻量进程执行，但共用 Job 归属、日志、停止和完成通知。宿主核对实际 Shell、命令前缀、工作目录和环境与审批时一致；重点验证 Windows PowerShell／Bash 及自定义 Shell。过滤输出使用私有系统临时目录中的 `output.log`，不造第二份日志或索引。前台结果保留当前直接输出的体验。正常完成通知保留；是否另行精简其正文，与消除主动停止后的重复通知分开决定。

## 归属、停止与输入

- Go 后端继续拥有终端资源、落盘终态和清理确认。Harness `AsyncShellHost` 继续拥有执行租约、任务归属、通知和 Subagent 等待；不新增持久状态账本。导航、退出和续跑维持现有代次围栏，交接结果未知不重放。
- `job_stop` 先认领本次停止的结果交付。在停止调用能够报告相同取消结果时，Harness 消费该 `cancelled` 回调完成内部结算与唤醒，但不再次向模型送入文本。正常结束抢先、停止失败或调用被取消时，不能用「曾请求停止」无条件吞掉结果。用同一个 Job 的现有归属记录处理 stop 与回调交错，不把清理失败当作停止成功。
- 启动沿用命令审批。向运行中的程序送文本或按键可能提交命令（包括 `enter: true` 和单独的 Enter）；这不是只读操作，也不能靠判断某个按键来判定安全。实装前对齐现有审批如何覆盖模型主动输入；不要通过直接调用后端跳过它。CLI 仍可供人使用；是否保留在模型指导中的 CLI 用法，与模型新入口分开决定。

## 实施顺序与验收

1. **Shell 入口**：保留既有审批；由 Harness 决定可配置等待阈值，复用 Go 的执行与完成路由。通过真实工具入口验证阈值内完成、按配置自动后台、显式后台、前台超时；用一次性副作用证明同一命令只启动一次，并验证日志可用 `read` 按行读取。测试使用短阈值，不等待默认 60 秒。
2. **Job 控制**：先接 `job_stop` 并消除重复取消结果，再接 `job_send` / `job_key`。验证跨 Actor／代次拒绝，同步结果与回调两种顺序，抢先自然完成，未知清理；输入测试验证文字原样、默认不发 Enter、显式另发 Enter。
3. **Go daemon 独立演进**：现有后端跑通接口后再测每任务 monitor 的启动和资源成本。若采用 daemon，建议每个 Harness 宿主管一个 daemon、多个 Job；先保留每 Job 的终端隔离和清理归属。单一受管连接传低频控制与终态，输出继续落盘，不经 IPC 逐行中转。先测启动延迟、并发与通知开销，再决定协议细节。daemon 死亡不是任务已退出的证明，不自动重启或重放状态未知的启动命令。

第一、二步不依赖 daemon；验收应覆盖两种后端的终端检测、默认 stdin EOF、非 PTY Job 拒绝输入。平台差异需在 Linux、Windows 实际运行，macOS 验证 Socket 长度与清理。
