# 尾部文本工具接口与 fallback 提案

**状态：探索性提案，刻意保留未完成部分。配置与 fallback 还没有明确想清楚；尚未实现，也不作为实施授权。**

下文实验验证了一种可能的传输方式。生产策略、自动能力判断和安全降级方案仍未确定。当前已实现的传输行为见[Provider 传输行为](../provider-transports.md)。

## 问题背景

标准 Chat Completions 通过顶层 `tools` 数组接收工具定义。新增发现的工具或替换 schema 时，头部模型上下文可能变化，从而使原本可以复用的缓存前缀失效。

部分端点支持原生消息内工具声明。另一些端点支持对话中途的普通 system 消息，却忽略消息内的 `tools`。网关也可能接收这类扩展，再把定义搬到顶层工具列表。因此，请求被接受，并不证明上游保留了声明位置或缓存前缀。

候选思路是固定初始顶层工具列表，把新工具的完整接口作为普通 system 文本追加到尾部。模型据此返回原生 `tool_calls`。本地运行时仍持有真实工具注册、当前 schema 和执行准入；文本定义本身不授予执行权限。

## 已验证的现象

以下结论来自 Pi SDK 1.5.0 下的小规模合成在线实验。实验没有执行模型返回的工具，后续工具结果均为合成数据。本文不包含凭据或本机隐私路径。

| 路径 | 观察结果 | 验证边界 |
| --- | --- | --- |
| Pi 原生 DeepSeek provider，官方 `deepseek-flash` 别名 | 对话中途的普通 system 指令生效 | 不能据此认定它与网关中相近名称的模型属于同一部署 |
| 同一官方端点，Pi 发送带 `tools`、不带 `content` 的 system 消息 | HTTP 422，提示缺少 `content` | 原生消息内工具追加格式被拒绝 |
| 同一官方端点，消息内 `tools` 配合空或普通文本 `content` | HTTP 200，但模型未识别新工具 | 接收额外字段不代表支持其语义 |
| 同一官方端点，完整工具接口写入尾部 system 文本 | 返回原生工具调用，随机函数名和两个随机 schema 常量全部正确 | 仅验证非 thinking、非 strict 模式 |
| Magpie `auto/deepseek-v4.1-flash`，实际观察到 WorkBuddy 路由 | 消息内声明的工具可以调用 | Magpie v0.1.3261 源码会把声明搬到顶层工具列表 |

官方文本接口实验设置了两种对照：顶层声明目标工具的正对照，以及完全没有目标定义的负对照。负对照返回 `UNAVAILABLE`。尾部文本提供接口时，`tool_choice: auto` 和 `tool_choice: required` 都返回正确的原生调用。原始供应商流中包含工具调用增量；实验没有把类似工具调用的普通文本解析成调用。

实验还把未在顶层声明的函数调用连同合成结果回传。端点接受了这段历史，模型准确返回结果标记。之后在尾部追加同名函数的新 schema，替换两个常量并新增第三个必填参数。模型使用了新版 schema，第二次合成结果往返也成功。

整个往返中，序列化后的顶层工具列表完全相同，每次请求的完整消息数组都是下一次请求的精确前缀。后续请求观察到了缓存读取。这些结果只描述该样本，不代表长期可靠性或普遍的缓存命中保证。

## 候选方向，尚未选定设计

未来的适配可以考虑：有效端点支持原生增量声明时使用原生机制；独立验证过文本接口能力时使用文本声明；其他情况使用标准顶层声明。

文本接口与 `supportsMidConvoToolAdditions` 是不同的机制。开启现有 SDK 兼容位，会让 Pi 发送消息内 `tools`，而本次测试的 DeepSeek 官方端点不支持这种格式。本文没有重新定义该兼容位的含义。

配置表示尚未选择。`auto`／`text`／`standard` 选择器、额外布尔开关、默认策略和根据模型名推断能力，都只是讨论过的可能性，不是已确定接口。

## fallback 为什么还没有想清楚

文本声明失败时，不一定出现明确的 API 错误。端点可能返回 HTTP 200，但模型只输出文字、不调用工具、沿用旧 schema，或构造错误参数。其中一些表现也可能是合理的任务选择。仅凭没有工具调用，无法区分“不支持”和“模型主动不调用”。

切换回标准声明会改变头部工具列表。降级后的上下文边界与历史回放方式尚未确定，也不能再声称保留了此前的缓存前缀。反复切换策略还可能持续破坏前缀。

重试语义是另一个问题。超时或断连不证明已经提交的操作没有入队；后续生成失败，也不证明本轮较早的工具调用没有执行。改变声明方式不能成为重放整轮或重复未知结果操作的依据。

这些问题尚未解决，所以本提案还不具备实施条件。给配置项取名 `auto` 并不能消除这些不确定性。

## 未决问题

- 什么证据足以对某个端点、模型、thinking 模式和 schema 模式启用文本接口？证据过期后如何处理？
- 能力信息由谁维护：provider 目录、网关、Pi、Harness，还是用户覆盖？如何避免普通使用时反复手动配置？
- 自动探测是否适合进入产品？如果适合，何时运行，如何呈现延迟、成本和无法判断的结果？
- 什么条件足以触发降级？什么时候保留不确定性并报告，而不是静默切换声明方式？
- 策略固定于会话、上下文边界，还是物理路由？网关在会话中途更换上游时如何处理？
- 恢复、分支导航、继承会话和压缩如何保留策略变化，同时不改写已经发送的前缀？
- 降级时保留哪些状态？如何区分已完成、已拒绝和结果未知的工具操作，避免盲目重放？
- 旧文本接口如何被新版覆盖或撤回？何时重建 checkpoint 比继续累积接口文本更合适？
- strict schema、指定名称的强制工具选择、并行调用、thinking 模式，以及会校验返回函数名的服务商，各自如何处理？

后续验证范围包括真实 Harness 执行及其当前 schema 和准入检查、长会话、接口变更、压缩、恢复，以及确定和不确定的降级结果。这是待验证范围，不是实施计划或已批准的状态机。

## 证据与复现参考

- [DeepSeek 工具调用说明](https://api-docs.deepseek.com/guides/tool_calls/)：普通中途 system 消息支持。
- [Kimi 动态加载工具](https://platform.kimi.com/docs/guide/use-dynamic-tool-loading)：另一种原生消息内工具格式，有明确的模型限制。
- [本次检查版本的 Magpie 消息工具转换](https://github.com/yetone/magpie/blob/83d9ee892daf503a827a195cf931bf60a2315f80/internal/gateway/message_tools.go)：网关接收声明、但将其搬到头部工具列表的源码证据。

合成实验使用随机函数名与必填随机 schema 常量，名称和常量只出现在工具定义中。顶层固定一个无关工具，另设缺少目标定义的负对照和标准声明的正对照。出站请求与原始工具调用流共同提供判定依据，结论仅覆盖实际测试的端点和模式。
