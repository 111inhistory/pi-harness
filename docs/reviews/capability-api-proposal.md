# 提案：Capability 业务 API 与继承检索边界

状态：方向性提案，暂不实施。本文不定义具体接口、类型或方法签名，也不改变[当前接口契约](../interface-contract.md)与[模块所有权](../architecture.md)。后续结合实际调用方完善。

## 目标

为 Capability 整理明确、可复用的业务 API，减少外部模块对内部操作顺序与装配细节的了解。优先收敛已有操作，不新增一套工具访问服务或统一大接口。

RPC、命令、模型工具与其他内部模块可以调用同一份业务 API。RPC 只承担协议校验、调用者绑定、结果传输与连接订阅；业务状态、执行顺序和权限规则继续由领域模块拥有。

## 常规操作

目录、权限查询、用户 enable／disable／reset 等操作优先复用已有领域入口，整理调用边界和结构化结果即可。暂不因这些操作被多个模块使用而另外拆分一个工具访问领域。

核对 RPC 适配与内部调用时，收掉仅作重复转发的包装；保留必要的协议转换、错误映射和连接资源管理。API 是否需要调整，以真实调用方的需要为依据，不机械地为每个函数增加接口层。

## Inherited 检索会话

Capability 的继承检索是需要额外梳理的边界。调用方不应自行拼装以下过程：

- 捕获父会话上下文，确定实际模型与继承缓存身份。
- 准备独立的内存 SessionManager 与检索专用资源装配。
- 过滤继承声明，保持检索工具与父工具执行能力的隔离。
- 管理取消、会话切换失效、清理及结果发布前复核。

Capability 拥有检索会话的具体装配和生命周期。它可以复用上下文继承、SDK 执行清理与预算原语，但不进入普通 Subagent 的角色路由、Actor／Job 注册或名额管理。普通 Inherited Subagent 的领域职责仍由 Subagent 拥有。

本提案不要求合并两类会话工厂，也不预设新增通用会话框架。

## 保留的约束

- 权限、发现记忆、运行时激活与声明资格保持各自语义；复用 API 不扩大授权。
- 保持记录先于生效、祖先与深度限制、代次围栏及确定性资源释放。
- RPC 与其他调用方共享权威状态，不建立独立业务状态机。
- 结果未知的消息交接不自动重放；接口整理不引入兼容别名或旧实现转发层。

## 后续完善

先列出 Capability、Subagent、Preset、BTW、命令与 RPC 的实际调用点，区分可直接复用的业务操作和需要隐藏的继承装配细节，再确定 API 的输入、结果、所有权与错误语义。

届时重点确认继承检索需要调用方提供哪些上下文、哪些信息应由宿主绑定，以及会话失效后何时允许返回结果。验收应经过真实 SDK／扩展加载与业务入口，覆盖不同调用方行为一致、父子状态隔离、取消清理和旧结果禁止发布。具体接口设计与实施拆分留待后续讨论。
