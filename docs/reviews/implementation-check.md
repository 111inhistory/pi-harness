## 已验证的主要路径

- Subagent 与 Capability 共用执行会话的创建、取消和清理入口。
- 初始化过程中退役服务，不会在创建结束后重新发布已退役服务。
- 正常完成、取消和失败均产生宿主终态通知。通知接收者是拓扑父节点，不是临时唤醒该 Agent 的同级节点。
- 忙碌 Main 与忙碌 Subagent 父节点均能接收合并后的进度和终态；不同轮次分开投递。
- 普通 Esc 后，后续终态通知可以沿原生 steer 路径唤醒 Main。
- 路由期间的消息不丢失；遗留队列完整回收；回放保留合并内容、自定义类型和宿主元数据。
- 受管理写入接收纯文本；多行和 JSON 文本不能修改发送者身份。普通文件和外部 Socket 保持各自语义。
- Unix 根目录和端点校验、活跃端点保护、失效端点回收、半帧连接关闭、重复关闭和替换端点保护均有隔离测试。
- Capability 的嵌套调用保存分支记录；旧会话保留回退读取；记录写入失败时不激活工具、不返回成功。
- Capability 只搜索本地资源，失败结果保留简短原因。同名工具更新后的 schema 进入实际 Responses 请求。

## 原生发现边界回归

本轮新增四项行为回归，不恢复此前删除的提示词措辞快照：

- `test/typed/capability-native-discovery.test.ts` 的两个加载顺序用例：实际 SDK 注册、MCP 传输与工具调用管线；Codemode 可启用，沙箱及动态函数均无法访问 `searchTools`。
- 同组验证并行基础读取、选中 MCP 调用、模型辅助函数用量、分支 `store` 和晚注册服务器。未选服务器不进入枚举与接口查询，晚注册不会重开原生搜索。
- 同组验证通用资源读取：选中服务器成功；未选、未知和不支持资源的服务器失败，错误正文不包含全量服务器目录。当前角色拒绝服务器工具后，历史选择也不能恢复资源读取。
- `test/typed/capability-codemode-boundary.test.ts` 验证真实 SDK 生成的旧 Codemode 目录在请求投影中移除，不修改用户正文或历史原件。
- 同文件用真实沙箱 worker 验证已唤醒的等待者取消后，后续脚本能取得空闲名额，不等到超时。

独立只读复核发现并复验了资源读取、历史目录和 worker 取消三个缺陷。修复后四项回归通过。测试不证明真实模型能正确选择资源，也不覆盖只有资源、没有工具的 MCP 服务器。

## 唯一失败：Main 无事件清空原生队列

失败测试为 `upstream-main-clear`，位于 `test/subagent-integration-real.test.mjs`，场景实现位于 `test-support/subagent-sdk-scenario.mjs`。

复现命令：

```sh
node --import tsx --test --test-name-pattern='clearing an ordinary native' test/subagent-integration-real.test.mjs
```

复现顺序：

1. Main 的模型调用保持忙碌。
2. 子 Agent 发送进度，宿主将自定义 steer 放入 Main 的原生队列。
3. 调用 `session.clearQueue()`，但不结束 Main、不发送新输入。
4. 子 Agent 完成任务。
5. 协调器仍将终态合并到已经移除的批次，Main 收不到终态。

Pi 1.4 的扩展上下文不提供 Main 的 `AgentSession` 或队列清空事件。`ctx.hasPendingMessages()` 只统计文本输入镜像，不能判断自定义 steer 是否仍在队列中。因此不能把该方法作为队列探针，否则会破坏正常的消息合并。

受管理 Subagent 会话由本项目创建，可以通过公开 Agent API 和 Job 缓冲区按批次检查消息。Main 不具备同样的访问条件。

下一步需要宿主提供同步队列清空通知，或公开原生队列清空修订号供扩展检查。项目随后可关闭旧合并键，让后续内容通过新的原生 steer 投递。该宿主接口变更尚未纳入实现。

本轮保留失败断言，不跳过测试，不用通知专用的取消许可状态掩盖缺口。当前 `npm run check` 不能视为通过。
