# 项目目标与整理范围

## 项目目标

Pi Harness 的核心是 Tool／MCP／Skill 的按需搜索，以及 Subagent。

- 按需搜索：主 Agent 先理解任务；存在缺口、否则要自行摸索或重复造轮子时，才调用 Capability 补足工具、能力、指引和信息。已有资源足够时不重复检索。内部检索不向主 Agent 展示全量资源目录和检索过程。
- Subagent：主 Agent 把任务交给子 Agent 执行；宿主自动通知任务完成，并提供用户查看入口。

远端 Capability 候选应转入用户审批，不返回主 Agent。上述通知、用户查看和审批要求不表示已经实现。目标契约与当前差异见[接口契约](interface-contract.md)。

Capability 与 Subagent 配套使用：Capability 的内部检索复用 Subagent 底层执行，不要求用户分别配置两套运行机制。公开工具是否注册或激活，不作为内部依赖的判断方式。

Shell Preflight 独立配置和使用，是附加功能，不是项目主线。Work 相关代码、测试和设计集中在 `experiments/work/`，属于暂缓方案。Work 能力仍有需求，但是否做成 Pi 插件尚未决定，不属于当前主线交付。

本节记录作者在本次文档整理中明确的目标。现有代码和旧文档不能替代作者的设计意图。

## 当前问题

### 工具提示词

作者认为部分工具提示词没有说明清楚工具的用法。工具提示词是本次整理的重点。

后续文档应分别说明：

- Agent 在什么条件下调用工具。
- Agent 提供什么输入。
- 工具返回什么结果。
- 调用是否等待任务结束。
- 调用成功不代表什么。
- Agent 如何取得后续结果。
- Agent 遇到失败或状态变化后能做什么。

上述条目是审查标准。工具行为说明已更新为纯文本通信和原生终态通知；提示词正文从执行代码外置到 `prompts/`。文本检查通过不等于多轮模型行为已完整验收。

### 内部架构与边界

作者认为内部架构存在问题，部分边界行为没有定义或实现完整。架构可能是边界问题的成因之一。

后续审查应同时检查职责划分和边界行为。不应先把问题归结为缺少判断分支，也不应只改提示词就认定问题已解决。

typed 核心、适配层和存储 v2 已接入。具体职责边界见[当前架构](architecture.md)，数据格式见[存储说明](subagent-storage.md)，未完成及未验证项见[已知问题](known-issues.md)。这些记录不代表全部边界已审计；用户查看界面和远端审批仍延期。

Shell Preflight 已覆盖 Agent 的 Shell 工具调用和聊天框命令入口。但覆盖入口不等于选对 Shell。

## 文档的事实边界

文档应区分以下内容：

| 类别 | 含义 |
| --- | --- |
| 项目目标 | 作者明确希望项目完成的事 |
| 当前行为 | 从运行环境或代码中核对的行为，并注明验证范围 |
| 已知 Bug | 已观察或已报告的错误，注明来源和验证状态 |
| 设计提案 | 尚未确认的方案，不写成既定要求 |
| 历史记录 | 旧方案和实验结论，不自动成为当前契约 |

旧文档已归档，不作为现行依据。作者已批准存储 v2 破坏兼容性，并使用独立脚本转换旧历史；运行时只解释 v2 事件，不自动迁移或恢复 v1 检查点。

## 整理顺序

1. 确认项目目标和术语。
2. 确认各工具的公开行为和边界。
3. 对照公开行为整理 Agent 实际看到的工具提示词。
4. 对照公开行为审查内部职责。
5. 只将核对并确认的内容写回当前文档。

具体接口和架构决定应在作者确认后写入对应文档。
