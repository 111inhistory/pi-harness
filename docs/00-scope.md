# 项目目标与范围

Pi Harness 是基于 Pi SDK 构建的 Coding Agent Harness 扩展。项目核心目标是提供按需发现工具与能力（Capability）、树状 Subagent 编排，以及受管本地 IPC 通信。

## 核心目标

### 1. Capability 按需搜索

- 主 Agent 应先理解任务与已有上下文。仅在存在明确能力缺口、否则需自行摸索或重复实现时，才调用 `capability` 检索。
- 检索过程和全量注册表不向主 Agent 暴露，避免无关目录干扰任务。
- 选中的资源通过分支上的 `capability-discovery` 规范条目累计保存。规范条目仍在当前分支时，请求投影可在压缩与嵌套调用后重建指引；记录不直接授予执行权限，激活记忆的已知缺陷见下文。

### 2. Subagent 树状编排

- 主 Agent 可将独立子任务交由子 Agent 并发执行。
- 子任务结束时，宿主自动向父 Agent 发送终态通知（`completed`、`cancelled` 或 `failed`），并携带本轮最终执行文本。
- 父 Subagent 正常回复结束后若仍有活跃直接子节点，当前 Job 保持 `running`。父节点在同一 Job 内等待子节点通知，暂停活跃时间计费，总存活租约继续计算，无需轮询。
- 支持多层派生、角色路由与候选模型分配；通过层级 Budget 约束模型调用次数、活跃时长与存活时间。

### 3. 受管本地 IPC 通信

- 统一通过专用的 `msg_write` 工具向受管端点发送纯文本消息；SDK 原生 `write` 工具保持文件写入语义完全不变。
- 宿主统一处理传输分帧与发送者身份绑定；调用方提供纯文本正文与目标地址。
- Unix 平台使用基于 UID 隔离且校验 inode 的 Unix Socket；Windows 平台使用命名管道。
- 同一用户、同一 Socket 根下的多个 Pi session 可通过已发布目录互相发现，并按对方 `Main` 的受管 Socket 路径由 Main 互相发消息；不提供跨主机调度或自动广播。该能力当前只在 POSIX 平台实现，Windows 明确不支持。
- session 生命周期编排（创建、恢复、停止、轮询、定时检查）由独立外部项目承担；本仓库只提供发现、寻址、消息与命名接口，不注册 `session_*` 工具。

### 4. Shell Preflight（附加功能）

- 独立配置与使用。拦截聊天框命令，Windows 环境下通过 PowerShell AST 校验后分发，防止命令选错 Shell。

## 待交付与实验状态

- **用户查看与控制入口**：面向用户的可视化查看、停止与干预界面仍未交付。面向模型的 `subagent_list` 接口仅供 Agent 查询拓扑，不能替代用户界面。
- **Capability 远端审批**：远端候选的审批对象、交互界面与安装流程未实现。当前仅搜索本地已注册资源，不向模型返回远端候选；覆盖状态标明 `not_searched`，不代表远端无资源。
- **Work 方案状态**：Work 实验代码集中在 `experiments/work/` 目录。交付形态尚未决定，主线不加载 Work，也不执行其测试。

## 非目标

- **不构建脱离 Harness 的外部调度服务**：Subagent 由同一 Pi 宿主管理，不提供跨主机的分布式调度集群。
- **不保留向后兼容包袱**：重构直接替换，严禁保留过渡包装层、兼容别名或旧版回退文件；存储运行时仅解释 v2 事件，不识别或恢复旧版 v1 检查点。
- **不维护外部 MCP 重连子系统**：MCP 外部服务的生命周期与连接恢复依赖 Pi 原生机制及用户的 `/mcp reconnect`，Harness 不维护连接守护。
- **不介入文件系统沙箱**：基础文件工具（`read`、`write`、`edit`）保持 SDK 原生行为与权限，不提供自定义文件虚拟层。
- **不盲目重发未确认消息**：IPC 写入异常或超时不证明消息未入队；只有明确尚未交出的同步拒收，才允许改走保留历史或重排路径。

## 验证与验收边界

- 生产代码位于 `src/` 与 `extensions/`，全部采用严格 TypeScript。
- 当前自动化回归主要基于真实 Pi SDK 与本地模拟模型，验证核心状态机、存储 v2 与进程级 IPC 通信。
- 真实供应商多轮在线压测、复杂网络波动以及 Windows 实机全套套件仍属于待验收场景，详见 [已知问题与验收边界](known-issues.md)。
- SDK `1.4.0` 的 allowlist 差异未解决。严格白名单下可能拒绝激活部分 MCP 工具，导致选择记录与实际激活状态不一致。
