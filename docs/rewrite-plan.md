## 四项选择的确认情况

以下四项已明确，不再单独设计通知的中断和唤醒规则。

### D1：消息合并到什么时候为止？

Main 执行工具时，子 Agent 可能先发进度消息，再结束任务。Main 下次继续执行时，应一次看到进度和完成通知，而不是先收到消息、又多等一轮才知道任务已经结束。

**已确认：消息写入 Pi 会话历史之前可以合并；写入之后不再修改，后来到达的内容另发一条。**

这里的“写入历史”不等于“模型已经读到”。采用这个做法，就不保证发出 API 请求前到达的所有消息都能合并。好处是不必接管 Pi 向模型发送请求的过程。

补充核对发现：Pi 的公开 `message_end` 事件可以在写入历史前，替换已经入队、甚至已经出队的通知。因此不必通过修改内部队列来更新通知，也不必只在入队前合并。

但该事件不是与历史写入绑定的原子操作。若后面的扩展仍在等待，期间到达的新内容不会自动加入已经返回的替换结果。候选实现应在通知定稿时结束这一组，后续另发；这个时点略早于历史写入，尚不能说与 D1 的字面截止点完全相同。七个对照实验见[steer 消息更新验证](reviews/steer-message-update-review.md)。

### D2：通知行为沿用 Pi steer message

**已确认的要求：中断、排队和后续执行都与 Pi steer message 保持一致，不另设通知专用规则。**

直接把通知作为 steer message 投递，是作者提出的实现建议，不是已批准的实现决定。本轮已查看现有代码，并用真实 SDK 验证：Main 执行工具期间、空闲时、一次中断结束后，都能接收带类型和附加信息的 steer 通知。正文、任务状态和历史路径均保留。

因此 Main 的 SDK 投递方式可行。若接收者本身是 Subagent，且其 SDK 会话已释放，还需经过现有运行管理代码启动续跑，不能仅改一个发送参数就认为完整功能已经接通。

本项目负责合并通知、标清来源与任务结果；Pi 负责排队和继续执行。不增加“取消后禁止通知”“等待明确恢复”等额外状态。合并可以在入队前完成，也可以通过公开 `message_end` 事件，在 Pi 保存对应通知前定稿；具体截止点的限制见 D1。

用户按 Esc 后如何处理，沿用 Pi 的行为，不再单独回答“必定唤醒”或“必定不唤醒”。关闭旧会话服务时，仍不能把它的通知发到新会话，这属于会话隔离，不是通知的取消策略。

### D3：广播保持什么行为？

**已确认：保留当前行为，不改成只向运行中的子 Agent 广播。**

当前行为是：

- 广播给发送者的全部直接子 Agent，不递归广播。
- 对每个接收者，使用与单独发消息相同的规则。已停止的 Agent 在允许续跑时启动新一轮任务，仍受并发上限等限制。
- 正在停止或收尾的 Agent 可以拒绝消息。广播返回每个接收者的成功或失败结果，不隐藏部分失败，也不自动重试。
- 接收者从父子关系中取得，不按查询列表的显示窗口裁剪。

代码依据是 `src/subagent-runtime.mjs` 的 `#broadcast`。重写保留这套行为。

### D4：审批功能没做之前，还搜不搜远端资源？

**已确认：先只搜本地资源，等用户审批功能可接收候选后，再开启远端搜索。**

返回结果应说明本轮没有搜索远端，不能说远端没有资源。

无论最后采用哪种做法，远端候选都不应返回 Main，也不应自动安装、加载或执行。

通知的规则不再继续细分，后续直接验证与 Pi steer message 的行为一致。

## 已验证与未验证

2026-10-24，在 Pi SDK `1.4.0` 上做过离线实验。模型回复和子任务事件由脚本模拟，没有请求真实模型。

已经确认：

- Main 执行工具期间，可以把子 Agent 的消息和完成通知合成一条。后续只需一次模型请求，会话历史也只增加一条消息。
- 带 `agent-completion` 类型和通知附加信息的消息可以通过 Pi steer 路径投递。Main 执行工具期间、空闲时，以及一次中断结束后，均已验证；每次新增一次后续请求，附加信息保留在历史中。
- 其它实验还验证了原生消息草稿和自行控制中断的做法，但这些不是当前选用的通知方案。实验记录保留供追溯，不转化成新的实现要求。

还没有验证完成：

- Pi 1.4 SDK Root 队列清空限制：上游未暴露 Root 会话的 `session.agent` 和队列清空事件。调用 `clearQueue()` 导致自定义进度消息丢失并影响同轮次终态。该问题保留为已知 RED 回归（`upstream-main-clear`），不宣称所有清空队列或 Esc 行为均已完全修复。
- 通知接入 Pi steer message 后，在用户中断、Main 即将结束和 SDK 自动重试时，行为是否与普通 steer message 一致。
- 真正切换分支后，旧通知是否仍留在旧会话，不会误发到新会话。
- 合并消息交给 Pi 时发生错误，是否能报告失败，而不是丢失消息或重复发送。
- 新的 Socket 清理方案、不同系统用户之间的隔离，以及 Windows 实机行为。
- 真实模型能否正确理解通知和工具说明。

实验记录见[消息投递验证](reviews/message-delivery-review.md)。这些结果说明方案可行，不代表当前实现已经修好。

## 实施顺序

下面每一步都先完成自己的测试，再接到实际流程中。新代码替代旧代码之后，只保留一套运行逻辑，不让两套代码长期同时写状态，也不一直依靠旧代码兜底。

### 第一步：固定开发和测试环境

先把本项目到底依赖什么写清楚，避免换一台机器就出现不同结果。

- 区分本项目自己的依赖和外层 Pi 环境提供的依赖，再决定哪些版本由本项目固定，哪些要求使用者提供。
- 先按已验证的 Pi Coding Agent／Pi AI `1.4.0` 开发，不同时升级 SDK 和重写代码。
- 列出当前使用的 SDK 内部接口，能换成公开接口的就替换；暂时不能替换的，注明升级风险。
- 改写依赖旧字段 `anchorsAdditions` 的测试，检查实际发给模型的工具定义，以及工具是否能执行。

完成条件：在干净环境中能装出同样的依赖；工具定义更新后，测试能检查到新定义，而不只是删掉报错的断言。

当前进展：Node.js `>=22.19.0` 与 Pi SDK `1.4.0` 已在 `package.json` 锁定；引入 `tsx` 与 TypeScript `5.9.3`，配置 `npm run check`（`typecheck` + `test`）。当前全量测试原有失败项留待重写替换后由 Main 统一复测，不直接宣称全部兼容。

### 第二步：集中保存 Agent 状态，明确任务何时结束

由同一处代码保存 Agent 的父子关系、每轮运行状态和任务结果。一次任务执行算一轮，续跑算新一轮；切换会话或分支时启动的新服务，也要和旧服务分开。

- 一次创建多个 Agent 时，要么全部登记成功，要么一个都不登记。
- 保留并发和层级限制，以及不继承历史、继承历史两种创建方式。
- Fresh 的思考强度直接读取配置中的 `thinking` 值，删除 `min`／`max` 区间和裁剪逻辑；Inherited 继续继承父会话的强度。
- 由同一处代码判断任务是完成、取消还是失败，不让执行器和历史写入代码各自决定。
- 任务结果定下来后，不因历史写入失败而改成另一个结果。
- 关闭旧服务时，先拒绝新任务和新消息，再停止运行、释放资源。旧回调不能转而修改新服务。

完成条件：测试覆盖取消、预算耗尽和正常结束先后发生的情况；任务处于 `finalizing` 时，结果不能再改；连续切换会话后，仍能关闭当前服务。

当前进展：`src/subagent/lifecycle.ts` 已实现 `firstEffectiveStopping`、`adjudicateTerminal` 与 `terminalNotification`；`src/subagent/routing.ts` 实现候选直选思考强度并移除区间裁剪；`src/subagent/execution.ts` 集中管理会话生命周期与清理。这里先保留现有的停止顺序：取消前会检查预算；已经进入 `stopping` 后，保留当时记录的停止原因。这不是“预算耗尽无论何时都覆盖取消”。改写前先用测试把这个区别固定下来。

### 第三步：补齐会话、历史和通信连接的清理

谁创建资源，谁负责释放；创建成功后，立刻把资源交给清理代码，不能等后续检查通过才接管。

- SDK 会话创建成功后，即使下一次预算检查抛错，也应能释放会话。
- 历史写入中只要失败过，就保留失败记录。最后一次写入成功，不能掩盖前面丢失的内容。
- 关闭通信服务时，先停止接收新连接，再主动断开已有连接，最后清理自己创建的 Socket。
- 不同系统用户使用各自的私有运行目录，并检查目录归属和权限。
- 同一个会话已被一个进程占用时，第二个进程不能覆盖它的 Socket。先用两个进程验证占用和退出规则。
- `write`／`msg_write` 接收地址和纯文本，由工具补上发送者信息与传输格式。`write` 写普通文件的行为不变。

完成条件：会话创建后出错仍能释放；历史写入错误仍可查询；客户端不主动断开、或只发了半条消息时，服务也能关闭；多行文本和 JSON 文本不会改变发送者身份。

当前进展：`src/ipc/endpoint.ts` 已实现用户私有目录（`0700`）、失效 Socket 安全探测与回收、inode 属主校验及连接安全释放；生产实现接入显式根目录校验与基于原子硬链接（atomic hardlink no-replace fail-closed）的安全创建机制；`src/ipc/message.ts` 实现宿主分帧的纯文本传输。IPC 根目录跟进修复正在收尾。

清理测试还要覆盖普通文件、符号链接、正在使用的 Socket 和失效 Socket。连接失败、超时、权限错误或找不到 PID，都不能单独成为删除路径的理由。不能确认归属时应拒绝删除，不能靠放宽权限解决。

这些测试使用隔离目录，不修改开发者正在使用的运行目录。不同用户和 Windows 的行为应单独验证，不能拿 Linux 单用户测试代替。

### 第四步：把普通消息和完成通知放在一起发送

每个接收方的待发送消息集中放在一处。同一个子 Agent、同一轮任务的消息和完成通知可以合并，不同轮次不能混在一起。

- 任务结束后，由管理任务状态的代码产生通知。通知文字不反过来决定任务是否成功。
- 使用 Pi steer 路径投递通知。合并同一子任务、同一轮次的内容；入队后的更新可以通过 `message_end` 返回替换消息，不直接改 Pi 内部队列。
- 按 D1 说明通知何时定稿，晚到的内容另组投递。这个实现截止点尚需确认，不假装与物理写入历史完全相同。
- 使用 Pi 自带的排队、中断和后续执行，不再维护另一套通知执行状态。
- 发送前检查旧会话服务是否已经关闭，避免把旧通知交给新会话。
- 检查交接失败的错误，不把调用返回等同于模型已读；不因模型尚未读取就重复发送。
- 这次不增加自动重试和永久收件箱。

完成条件：正常完成会自动通知；工具执行期间的消息与完成通知能合并；不同执行轮次不会混合；中断和后续执行与 Pi steer message 一致；旧会话的通知不会发到新会话。

当前进展：`src/subagent/delivery.ts` 已实现 `createSteerDelivery`（按来源与轮次归集未投递内容，在 `message_end` 封口前与终态通知合并）；适配层已接通终态通知与空闲唤醒续跑。投递协调器已连接 native input、`message_start`、`agent_end`（aborted）与 `agent_settled` 边界，受管理的子 Agent 会话使用 `agent.hasQueuedMessages()` 探针处理队列清空。Root 侧受限于 Pi 1.4 SDK（无 `session.agent` 与清空事件），程序化 `clearQueue()` 导致自定义进度丢失的问题仍保留 `upstream-main-clear` 为 RED 回归测试作为证据。普通 Esc 作为独立场景（`upstream-main-esc`）测试，严格的 `busyParent` 合并正由 Main 补充测试。不宣称所有清空队列或 Esc 场景已完全修复。

### 第五步：让 Capability 复用 Subagent，并记住已经发现的资源

Capability 的检索 Agent 直接复用 Subagent 的底层执行代码，不再自己创建和清理另一套 SDK 会话。

两者配套装配和配置。Capability 调用内部执行入口，不要求公开的 `subagent_create`、`subagent_list` 或 `subagent_stop` 已注册、已激活，也不通过这些工具执行内部检索。

- 启动、预算、取消和清理复用 Subagent；Capability 只负责检索任务、候选筛选与结果分流。
- 保留检索 Agent 的隔离和工具限制，不因复用执行代码而扩大权限。
- 成功发现的资源由本项目写入当前分支的记录。即使 Capability 是由另一个工具间接调用，外层没有保留它的 `details`，发现结果也不能丢。
- 给模型的资源指引从这份记录生成，不再另存一份可独立修改的清单。
- 发现记录不等于执行许可。每次调用仍检查当前角色和工具权限。
- 同名工具的参数定义更新后，把新定义交给模型，不能为了保留缓存而继续使用旧定义。
- 远端搜索按 D4 的决定处理。远端候选不能进入 Main 的工具结果、能力记录或摘要。
- 检索失败时，告诉 Main 可理解的失败原因，不返回全量目录和内部排序过程。

完成条件：同一套装配提供内部执行能力，不靠公开 Subagent 工具判断能否搜索；检索实际复用 Subagent 执行代码；直接或间接调用都能保存发现；再次搜索不会减少已有资源；不同分支不串资源；权限检查仍有效；发给模型的请求包含新版工具定义。

当前进展：Capability 已复用 `openSubagentExecution` 共享执行，无公开工具注册门禁；落实 D4 本地搜索；`src/capability/discovery-record.ts` 规范化分支记录，解决嵌套调用丢失并支持旧记录回退，不复制参数 schema，请求时动态校验工具注册表权限。这一步只解决本项目的能力记录和工具声明，不修压缩插件，也不靠重新调用 Capability 掩盖其它上下文丢失。

### 第六步：同步提示词和测试，删除被替代的旧代码

- 删除按任务语言拒绝创建的检查。英文只保留为路由器的使用推荐。
- 按读者整理提示词，移出执行代码，不为此新增模板框架。
- 改写与目标相反的测试，例如“正常完成不通知”“调用方填写 NDJSON”“远端候选返回 Main”。
- 复用仍有价值的预算计算、历史继承、Skill 索引和历史读取逻辑，不照着旧文件结构搬代码。
- 确认没有调用方依赖旧代码、替代测试也已齐备后，再删除旧代码。
- Shell Preflight 独立配置和使用。Capability 与 Subagent 配套配置，不拆成两套运行机制。
