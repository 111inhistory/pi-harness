# 新架构草案

## 状态

**本项目重写总体架构，按行为复用旧代码。旧模块和调用链不约束新设计。**

本文是供确认的架构草案，不表示已经实现。产品要求以[接口契约](interface-contract.md)为准；缺陷证据见[核心架构 Review](reviews/architecture-review.md)。

本文先确定状态所有者、调用方向和资源寿命，不先建立通用框架。职责可以用函数和闭包表达，不要求每项职责对应一个类。

实施切片与设计选择见[重写计划](rewrite-plan.md)。部分实现已接入；验证范围和未关闭缺口见[核心实现验证记录](reviews/implementation-check.md)。

## 设计约束

- Capability 的检索 Agent 由 Subagent 的底层执行代码运行，不再另建一套会话创建、预算、取消和清理流程。
- Capability 与 Subagent 配套装配和配置。内部调用不依赖公开 Subagent 工具是否注册、激活，也不要求用户配置两套执行环境。
- Shell Preflight 独立配置和使用，不依赖上述执行流程。
- 每一类可变状态只有一个写入所有者。其他模块提交请求或读取快照，不直接修改状态。
- 创建资源的组件负责释放资源。取得资源后，先登记清理责任，再执行可能失败的检查。
- 消息和终态通知共用投递入口，不共用终态裁决权。
- SDK、IPC 和历史文件是边界，不是领域状态的决定者。
- 提示词独立存放，只描述行为，不承担权限或生命周期校验。
- 不引入通用事件总线、永久收件箱、消息回执状态机和自动重试框架。

## 总体结构

```text
统一装配与配置
    │
    ├── Capability 入口 ──► 检索任务 ──────────┐
    │                                        ▼
    └── Subagent 公开工具 ──► 委派任务 ──► Subagent 内部执行
                                             │
                                  SDK 会话、预算、取消、收尾
                                             │
                 ┌───────────────────────────┴─────────────┐
                 ▼                                         ▼
         检索结果交回 Capability                   委派结果与通知
         筛选、分流、激活与返回                     历史、查询与投递

Shell Preflight：独立入口与配置
```

图中的连线是明确函数调用，不表示建立全局事件总线。

### 状态所有权

| 所有者 | 独占的可变状态 | 不负责 |
| --- | --- | --- |
| 会话宿主 | 当前根会话与分支、服务代次、激活与退役操作 | 判定任务结果、排序候选 |
| Subagent 状态核心 | Agent 拓扑、执行轮次、任务状态、停止原因、冻结终态 | SDK 对象、Socket、提示词和文件写入 |
| Subagent 执行器 | 委派任务与内部检索任务的 SDK Session、abort、订阅和预算观察器 | 资源检索策略、重新决定已冻结终态 |
| 投递协调器 | 接收方的待投递事件、交付中的批次、唤醒调度 | 修改任务结果、保存第二份聊天历史 |
| IPC 适配器 | 端点、连接、实例归属和传输封装 | 选择广播对象、决定是否续跑 |
| 历史写入器 | 本轮写链、写入错误、摘要收尾 | 把磁盘错误改成模型执行失败 |
| Capability 调用 | 本次检索上下文、候选、选择和取消状态 | Subagent 注册表、远端代码执行 |
| Pi 适配层 | SDK 接入、原生会话操作、分支成功发现记录、工具登记与激活 | 产品策略和任务终态 |

这里区分长期 Agent 与短期执行轮次。Agent 保存身份和会话引用；一轮执行结束后，可在同一 Agent 下启动下一轮。

同一信息不在多个模块各自保存一份可独立修改的真相。比如 SDK 是否流式输出是执行器的观察值，不是另一份任务状态机。

## 依赖方向

入口只组装对象、注册工具和转发事件，不在工具处理函数里完成全部执行流程。

- Capability 调用 Subagent 的内部执行入口，不通过 `subagent_create` 等公开工具，也不检查这些工具是否注册或激活。
- 统一装配代码把内部执行能力交给 Capability；不靠扩展加载顺序或工具注册表发现依赖。
- 公开扩展入口仍只注册工具和接入 Pi，不让 Capability 导入带注册副作用的扩展入口。
- Subagent 状态核心不导入 Pi SDK、IPC 或提示词资源。
- 执行器、历史写入器和 IPC 通过窄接口返回结果。
- 宿主协调生命周期，不允许 adapter 直接改状态核心的 Map。
- 投递协调器通过接收方适配接口提交批次，不自行创建 SDK Session。
- 提示词资源不导入运行时代码。

SDK 兼容细节仍放在 Pi 适配层，但 Agent 的启动、执行和清理由 Subagent 统一完成。不能只抽几个 SDK 辅助函数，却让 Capability 继续维护另一套执行流程。

Capability 提供检索任务、上下文和允许使用的工具，Subagent 负责运行。内部调用与公开委派共用执行代码，不因此把 Capability 调用改成公开 `subagent_create` 调用。Capability 仍等待检索结束再返回。

不为此引入通用插件系统，也不要求 Capability 和 Subagent 各自配置运行实例。

## Subagent 执行与收尾

### 执行流程

1. 校验整批输入和拓扑名额。
2. 原子登记 Agent 与首轮执行。
3. 按 Fresh 或 Inherited 语义构造执行配置。
4. 启动执行器。
5. 接收执行器退出结果。
6. 同步裁决并冻结终态。
7. 等待历史写入器收尾。
8. 发布本轮终态和历史状态。
9. 将终态事件交给投递协调器。

创建工具仍不等待任务完成。执行器创建 Session 后，应立即接管资源，即使随后的预算检查失败，也能释放 Session。

### 状态与结果

本轮执行保留 `running`、`stopping`、`finalizing` 和终态的区别。

- `running` 包括路由、资源加载和执行。
- `stopping` 表示停止已请求，但执行尚未退出。
- `finalizing` 表示执行已退出、结果已冻结，历史尚未收尾。
- 终态区分完成、取消和失败。

执行结果与历史状态分开保存。历史写入失败不改写执行结果，但通知与查询不能把历史标为完整可用。

本轮写入器应保留任意一次写入失败，而不是只检查最后一次写入。后续写入成功不清除早先的错误。

停止请求、预算耗尽和模型错误仍由状态核心统一裁决。当前代码在取消前检查预算，进入 `stopping` 后保留已记录原因；并非预算在所有时点都覆盖取消。迁移先保留这一区别，建立顺序测试，不让不同 adapter 各自解释。

### 退役

退役操作绑定具体服务代次，结束后释放操作记录，不复用上一代已完成的 Promise。

退役先禁止新任务和新消息，再请求本轮执行退出，并停止接收连接。执行收尾完成后，宿主保存最后快照并释放自有端点与句柄。

已有连接应由 IPC 适配器主动结束，不能无限等待客户端自行断开。单个清理步骤失败不应跳过其他资源的清理；错误应保留并报告。

所有回调携带原服务引用或代次，不通过全局“当前服务”把旧结果写入新分支。

## 消息与通知

### 消息入口

调用方只提交接收地址和纯文本。工具入口从调用会话取得发送者，正文不参与身份判定。

通信入口依次完成：绑定调用身份、解析受管理地址、校验投递资格、构造内部消息、交给接收方投递协调器。

多行文本和 JSON 字面文本都是同一条消息的正文。内部可以使用 JSON，但 Agent 不填写传输信封、换行或发送者字段。

广播目标由 Subagent 拓扑与明确的广播策略决定。列表窗口和 listener 缓存不决定接收集合。作者已确认 D3 保留当前行为：广播到全部直接子节点，每个接收者沿用单独发送的接收与续跑规则，仍受并发上限等限制。停止节点不因状态被排除，但正在停止或收尾时可以拒绝消息。返回每个接收者的成功或失败，不自动重试。

### 待投递事件

普通消息与终态事件共用一个接收方入口。宿主终态与 Agent 文本保持可区分，普通文本不能冒充宿主结果。

待投递项至少标识接收方、源 Agent、源执行轮次和内容顺序。具体字段名属于实现设计，不新增为模型输入参数。

同源、同轮次的消息与终态，在尚未交付时合并为一个模型可见项。不合并不同轮次，不覆盖父 Agent 已看到的内容。

### 交付边界提案

**已确认：以 Pi 会话历史确认写入作为批次不可修改的截止点，而不是排队函数返回或模型已读。** 见重写计划 D1。

此前草案候选是下一次模型请求。补充验证表明，SDK 提供更早的原生边界提交，而请求投影既不持久化，也不提供模型接收确认。因此已确认缩小承诺，不为追求 HTTP 请求前的绝对合并而接管供应商发送。

如果 Main 执行工具，普通消息先留在协调器。子任务在批次交接前结束时，协调器把消息与终态作为一项提交；已提交后到达的事件进入下一批。

**D2 已确认沿用 Pi steer message。** 协调器负责通知内容合并，不重建 Pi 的执行控制；直接投递一条 steer message 是候选实现，SDK 层已有通过验证；它不是作者已批准的实现决定。Pi 负责忙碌时排队、中断和后续执行，本项目不再维护另一套通知唤醒与恢复状态。

交接前确认接收方仍属于原会话服务，不通过全局“当前会话”转投旧消息。交接后不修改 Pi 内部队列，也不自行启动并发的父 Agent 执行。公开 `message_end` 事件允许在历史写入前返回同角色替换消息，可用于入队后定稿通知。交接失败应报告错误，调用返回不等于模型已读。

该替换方式已有七个离线对照：能覆盖消息仍在队列、已出队但尚未保存，以及同时存在用户消息的场景。但处理函数返回与真正历史写入之间仍有异步间隔；期间新到内容不会自动合入。实际定稿截止点与 D1 的历史写入截止点不能直接等同。详见[steer 消息更新验证](reviews/steer-message-update-review.md)。

SDK 接管已提交内容，不要求模型确认读懂，也不承诺跨进程的恰好一次投递。取消发生在提交之后时，不把原生历史中的批次当成未读消息重复发送。

尚待验证合并消息交接、Main 即将结束时的投递，以及真正分支切换。不为规避这些边界新增永久收件箱、模型已读回执或自动重试系统。

父 Agent 等待 children 时只需结束当前回复。通知负责唤醒，不增加 `sleep` 或阻塞式 `wait`。

### 已完成的局部验证

已用 Pi `1.4.0` 的真实 SDK 离线验证工具执行期间的单子任务场景：分别提交消息与通知，会占用两次后续模型请求；先暂存事件，在 `turn_end` 中合为一条原生消息，则下一次请求同时看到消息与终态，历史中也只保存一项。

直接返回原生 `custom_message` 草稿与继续执行标记也已验证。最终回复后的通知应请求继续，不能沿用加入草稿前的 `canContinue`。

取消与代次实验、原生消息草稿实验保留在[投递边界验证](reviews/message-delivery-review.md)中。它们不是选用方案：不因做过实验，就引入额外的取消许可或草稿提交协议。

下一步使用原生 steer message，不重写父 Agent 的执行循环。`turn_end` 等事件只用于确定交接前的合并时点，不承担自建的执行许可判断。

### 消息保存与恢复边界

核心阶段只要求运行期间的待投递协调，不新增永久消息数据库。

进程重启后不自动重放通知。消息已进入原生会话时，沿用原生记录；尚未提交的内存事件不宣称可恢复。

D2 已明确：通知交给 Pi steer message，沿用 Pi 的中断和后续执行行为。不增加“保留通知但禁止唤醒，等明确恢复”的专用状态。

分支退役时不把旧分支待投递事件交给新分支。是否保存未交付事件留待后续需求，不借恢复之名加入消息重试系统。

## Capability

### 调用条件

Capability 不是每个阶段的固定前置步骤。Main 发现能力或指导缺口、否则要自行摸索或重复造轮子时，才调用检索。

已有发现足以继续工作时，应直接复用。切换到文档整理、Review 或架构设计，不单独触发再次检索。只有新需求尚未覆盖、已有资源不适用或不可用时，才重新调用。

此规则写入 Main 的使用指导，不以阶段计数器、冷却时间或额外状态机限制调用。

### 流程

1. 捕获调用方的任务上下文与当前工具资格。
2. 通过 Subagent 内部执行入口启动隔离的检索 Agent。
3. 搜索并筛选工具、Skill 和指引。
4. 校验选择来自本次检索结果。
5. 分开本地可用资源和远端候选。
6. 按当前资格激活已注册的本地工具。
7. 返回精简的本地资源与可理解的错误。
8. 由 Subagent 的执行清理代码释放检索会话和订阅。

内部检索只执行检索与提交选择的工具，不持有父 Agent 的执行句柄。检索权限通过 Subagent 的内部运行配置传入，不能因为复用执行代码就开放普通子任务的全部工具。继承接口声明不授予执行权限。

检索、资源读取和激活是不同责任。资源目录回答“有哪些、如何读取”；检索流程回答“本次选择哪些”；Pi 适配层执行已允许的激活。

### 远端延期策略

远端候选在分流后不进入 Main 的工具正文、能力记忆或摘要。宿主诊断与模型可见内容也应区分。

审批入口完成前，核心不安装、加载或执行远端候选。作者已确认：没有审批接收方时关闭远端检索，并说明本轮只搜索本地，见重写计划 D4。

不能把远端候选过滤为空，进而声称“已经搜索且不存在远端资源”。返回错误和覆盖范围时应保持事实一致。

### 工具资格与提示词记忆

已注册、可发现、已激活和可执行是不同状态。执行时仍检查当前权限，历史能力记录不授予调用权。

Capability 在当前分支内只增不减。核心保留已选择的资源与加载结果，不因后续检索或 `compact` 缩减能力集合。本轮不设计能力撤销流程。

能力累积不替代权限检查。角色拒绝和宿主工具资格仍是执行边界，不从历史声明推导额外执行权限。

成功选择由宿主写入原生分支记录，不依赖外层工具结果是否包含内部 Capability 的 `details`。直接与嵌套调用使用同一记录入口。

请求投影读取这份分支记录，不另存一份可独立修改的能力清单。执行权限仍由当前宿主资格决定，成功发现记录不成为永久授权。

### 原生发现适配

**配套入口只保留 Capability 发现路径，不另建 MCP 连接后端。**

`src/capability/native-discovery.ts` 通过 Pi 的可替换扩展机制接入原生 MCP 后端。适配器保留认证、连接、用户命令和调用管线，取消默认目录注入与默认工具声明。原生 `tool_search` 和全局资源列表不可执行。服务器配置中的 `direct`、`codemode` 或 `deferred` 不绕过 Capability 选择；`hidden` 继续生效。

`src/capability/codemode.ts` 保留原生 Codemode 的参数、加载方式、渲染器和 `on`／`only` 模式。Pi 1.4 的原生执行器固定注册 `searchTools`，没有关闭选项。因此适配器复用 Pi 的公开 `CodemodeSandbox`，只注册受限的接口查询与模型辅助函数，不注册 `searchTools`。适配器不改写用户脚本来遮蔽搜索函数，也不实现第二套 JavaScript 引擎。

Codemode 启动脚本时确定可用工具，运行期间不增加新工具。`tools`、`ALL_TOOLS` 和接口查询使用同一份工具列表。如果脚本运行期间才激活新工具，新工具从下一次 Codemode 调用起可用。嵌套调用仍经过 `ctx.executeTool`，不直连工具句柄。成功脚本保留分支 `store` 写入，模型调用继续报告用量；适配器限制 worker 数、脚本内模型并发、内存和输出长度。

选择从当前分支规范记录重建，旧会话保留结果回退。适配器不维护另一份可修改的 MCP 许可清单。通用资源读取还检查目标服务器的选择，避免通过未知服务器错误取得全量目录。历史 Codemode 描述中的旧目录也在请求边界移除。

### API 协调与压缩恢复

原生压缩插件的兼容修复当前不在推进范围内，压缩方案由作者另行处理。以下保留能力恢复的目标，不把第三方压缩修复作为本项目重写的前置条件。

会话适配层统一协调能力记录、工具加载状态和供应商 API 声明。Capability 负责增加选择，适配层负责把已有选择正确呈现给模型，不让压缩恢复重新走检索。

`compact` 后应从当前分支恢复既有能力，并根据宿主注册表核对工具接口。只恢复 `<capabilities>` 文字不等于恢复了可调用工具。

主会话、Subagent 和隔离检索会话共用适配规则，但执行权限不同。检索会话即使保留父接口声明，也只执行检索与提交工具。

SDK 专属的缓存前缀投影放在这一适配层。Responses 的接口增量声明、压缩后声明重建和其他 API 的投影不散落在 Capability 的检索流程里。

在同一上下文段内，声明和指引宜追加而不改写已发送前缀。`compact` 会重建上下文，不承诺保留原缓存命中；但压缩后已有工具仍应立即可用。

先固定 SDK 基线，验证实际请求中的工具声明和执行权限，再测缓存收益。缓存优化可以复用 Subagent 所需的会话适配能力，但不依赖公开 Subagent 工具。

## IPC 与权限

Unix 运行目录应按有效系统用户隔离，并使用私有目录权限。root 与普通用户不共用一个由先启动者占有的可写根目录。

实例占有关系与逻辑 Agent ID 分开。短 ID 便于模型使用，但不能独自承担多进程排他和端点归属。

启动和退出都应验证路径归属。活跃端点、失效 Socket、符号链接和普通文件不能统一用盲目 `unlink` 处理。

两个进程恢复同一根会话时，提案是拒绝第二个实例占用，而不是抢占第一个实例的端点。具体占用检查机制留待实现前验证。

连接拒绝或超时不能单独证明路径归属；PID 存活检查也不排除 PID 重用。恢复应验证有效用户、路径类型、排他占有与当前实例身份；不能确认时拒绝删除。私有目录或探测步骤不能代替双进程竞争测试。

正常退出只清理自有端点、连接和空的私有实例目录。SIGKILL 后依靠后续启动安全识别失效资源，不承诺退出钩子总能执行。

Windows Named Pipe 使用独立平台实现，不照搬 Unix 文件删除规则。权限、实例区分和关闭连接的目标保持一致。

本设计不把“报文带有 `from`”当作身份认证。受管理工具从宿主上下文绑定身份；直接外部 IPC 客户端的身份能力与允许范围仍待明确，不承诺已经建立认证协议。

## 状态持久化

原生 Pi SessionManager 继续保存对话与分支。项目快照只补充 Agent 身份、拓扑、轮次结果和必要会话引用，不复制整份对话。

根会话身份账本跨分支记录已分配 ID。活动状态和消息投递则属于具体分支及服务代次，两者不混用。

恢复时，未结束的旧轮次标为中断，不自动重跑。派生历史可用于诊断，但不能覆盖注册表中的生命周期事实。

快照、历史和通知不承诺跨文件事务。写入失败应可见；已经持久化的旧事件也不能因此重复触发新执行。

## 提示词资源

提示词从执行代码中分离，按读者和用途存放：

- Main 的 Capability 使用流程。
- 内部检索 Agent 的搜索与选择规则。
- Subagent 的任务、通信和等待规则。
- 各工具的用途、参数说明和后续动作。

动态身份和路径通过显式参数填入，不散落在执行函数内拼接。工具参数 Schema 仍由代码定义，不把数据校验混入自然语言资源。

本轮不增加模板语言或热更新框架。资源格式在实现前选择能表达现有文本和少量参数的最小方案。

## 代码组织提案

```text
extensions/          # 公开入口与组装
src/capability/      # 目录、检索、资源读取、结果分流
src/subagent/        # 状态核心、共用执行入口、执行编排、投递协调
src/pi/              # SDK、上下文、模型环境、会话投递
src/ipc/             # 平台端点、连接与纯文本封装
src/history/         # 派生历史与写入结果
prompts/             # 按读者区分的提示词资源
```

目录不是额外抽象层。预算计算等深度模块可保持独立，不强迫所有代码经过统一基类或容器。

Capability 与 Subagent 在同一处装配，配置按配套使用设计；具体文件格式另定，不以目录划分强迫用户分别配置。Shell Preflight 保持独立的附加功能，不参与核心编排。`work`、原型和实验代码不因原来位于同一仓库而进入新核心。

## 复用与迁移

| 现有实现 | 复用前提 |
| --- | --- |
| Budget 计算 | 保留计数与终态语义，移除与旧入口绑定的部分 |
| 上下文捕获 | 保留原生条目、签名和分支语义 |
| Session 存储与恢复 | 保留行为，重接到单一会话宿主 |
| 历史格式 | 保留读取价值，重写写链错误汇总与收尾所有权 |
| 搜索、排序、Skill 索引 | 保留独立算法，拆开资源读取与公共结果分流 |
| IPC 平台实现 | 可复用寻址与编解码细节；重新设计归属、关闭和纯文本入口 |
| Runtime 校验与转换 | 按新状态核心迁入，不搬旧 URI 与语言硬拒绝 |
| 测试 | 保留行为保障，迁移接口；旧契约断言改写或删除 |

先固定依赖与测试基线，再建立会话宿主和状态核心。随后接入执行器、历史和消息交付，最后让 Capability 接入这套 Subagent 内部执行入口，并整理提示词资源。

迁移可以在独立内部切片中验证，但最终只保留一套活动编排。旧代码不成为永久 fallback，新接口也不长期通过旧状态机转发。

## 实现前的验证门槛

- 补齐合并消息通过 Pi steer message 投递的 SDK 组合测试，包括 Main 即将结束、用户中断与交接失败；不再验证自建的草稿提交或取消许可方案。
- 验证同一根会话的实例占用和端点清理方案，包含不同有效用户。
- 验证广播保留 D3 的当前行为，不复用查询窗口隐式决定。
- 验证 D2：通知与普通 Pi steer message 行为一致，不增加专用中断、恢复与唤醒规则。
- 验证 D4：审批接收方未实现前不搜索远端，也不向 Main 返回远端候选。

这些门槛不要求先实现用户界面或审批控制面。下一步按 D1–D4 简化本草案的职责划分，再补充 steer message 投递与会话隔离测试，随后形成可执行的迁移步骤。原生压缩问题已单独记录并暂缓，不阻塞上述工作。
